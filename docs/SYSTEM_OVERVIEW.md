# 현재 개발본의 구조: 무엇이 읽고, 무엇이 판정하는가

이 문서는 기존 `db045c5`에서 개선한 시스템의 설명이다. 최신 v104 변경과 게시 검증은
[RELEASE_20260929.md](RELEASE_20260929.md)를 우선 참고한다.
구현한 항목과 검증이 남은 항목은 `VALIDATION_SCOPE.md`에 구분했다.

v92에서는 실행 관리자 `pipeline.py`의 미사용 옛 검사41개를 정리해 2,615줄에서852줄로 줄였다.
사용 중인24개 정의의 로직은 바꾸지 않았다. 전체 코드 정리나 모든 판단의 MD 이전이 끝난 것은 아니다.
정리 범위·과거 감사표의 구별·전후 검증 방법은 [PIPELINE_CLEANUP.md](PIPELINE_CLEANUP.md),
최종 검사 결과는 [업데이트 기록](RELEASE_20260929.md)을 따른다. `WORK_STATUS.md`는 로컬 작업 이력이며 저장소에 포함하지 않는다.

v97에서는 시뮬레이션 그래프(`sp_flowchart_data.py`)의 **공정**과 **공통/미분류 판정 표시**를 분리했다.
실제 공정이 모두 대응하면 PDF 연결선을 사용하고, 공통 검증 숫자는 연결선 없는 기존 상자에 남긴다.
시험 판정이나 MD를 바꾼 것이 아니다. 자세한 선택 조건/오류 처리/남은 한계는 `SIMULATION_PREPARATION.md` 참조.

v98은 같은 표시 모듈에서 여러 공정도/순환·재작업 등 미지원 구조를 명확히 중단하도록 보완했다.
정상 비순환 분기·합류의 배치는 모든 선행 공정을 반영한다. 다중 공정도를 자동 병합하거나 새 시험 로직을 추가한 것은 아니다.

v99에서는 `sp_process_lock.py`를 추가해 **같은 제출 건을 다른 서버 프로세스가 동시에 판정하는 것**을 막는다.
기존 작업 큐는 프로세스 내부, 새 잠금은 프로세스 사이를 담당한다. 화면/판정 기준은 그대로이며
중단 작업을 단계별로 재개하는 기능은 아직 아니다. 동작·실패 재시도·한계는 `CACHE_FAILURE_RECOVERY.md` 참조.

## 1. 사용자가 보는 흐름

기존 메일 수신과 문서함·기준 SP 선택·검수 진행·최종 판정 화면은 유지한다.
상단 **파일 업로드**에서 SP PDF와 해당 SP의 허가서 PDF를 함께 등록할 수 있다.
한 번의 등록에서 연결한 허가서는 그 제출 건에만 사용한다.
허가서를 나중에 추가하거나 교체할 때는 같은 업로드 창의 연결 변경 기능을 사용한다.
이전 파일은 이력으로 남기고 현재 연결만 변경하며, 이전 판정은 재사용하지 않는다.

허가서가 여러 개라는 이유로 전부 다른 제출 건에도 적용하면 잘못된 기준을 찾을 수 있다.
따라서 직접 연결한 허가서와 기본 카탈로그의 허가서를 자동으로 섞지 않는다.

## 2. PDF 한 건의 처리 흐름

```text
SP PDF + 명시적으로 연결한 허가서
       ↓
추출: 본문·표·제조요약도 → 시험/내용/공정 레코드
       ↓
시험별 판정
  SP 자체 기준 비교 → 필요한 정성 해석
  → 권위 있는 허가서가 있으면 해당 단계·시험의 기준 대조
  → 원문 연결 검증 + 확정 가능한 수치 재계산
       ↓
MD 규칙 실행: 문서 간 일치·누락·날짜·단위·합계·사용자 의미 규칙
  (수치 결과 비교는 위 시험 판정의 검증된 허가 기준을 공유)
       ↓
규칙별 상태 + 시험별 상태 + 원문/페이지 + 적용 규칙 해시
       ↓
기존 UI 카드/요약/제조요약도에 표시
```

추출과 판정은 다른 작업이다. 예를 들어 숫자 `8.5`가 잘못 목차로 추출되면 그 다음 시험이 다른 제조단계에 연결될 수 있다.

같은 PDF를 여러 번 검수해도 추출 근거를 덮어쓰지 않는다. v72부터 요청별 고유 작업폴더에 추출 JSON/미리보기를 보존한다.
허가서 적용 전·후 판정처럼 추출을 재사용하면 두 결과는 실제 같은 원문 폴더를 참조한다. 다른 PDF의 결과는 재사용할 수 없다.
이 구분과 동시 처리 회귀시험은 [EXTRACTION_WORKSPACES.md](EXTRACTION_WORKSPACES.md)에 설명했다.

버전·날짜·페이지 번호만 있는 머리말 표가 시험결과 표로 섞이는 경우도 있다. v68 추출기는 이 좁은 형식을 분리하고,
명확한 프로토콜 제목과 같은 머리말 영역 안의 제조번호도 결과에서 제외한다. 시험값/알 수 없는 문구가 섞인 표는 통째로 지우지 않는다.
버전 셀의 `/31 페이지`처럼 분자가 잘린 형태도 구분하되, 원래 페이지 번호가 무엇인지를 추측해서 고쳐 쓰지는 않는다.
원본 추출 `pages`/`tables`는 그대로이며 `06_extraction_result.json`의 `extraction_cleanup`에 페이지·문구·표·위치·사유를 기록한다.
이 정리는 판정용 구조화 계층에만 적용되고 원본 PDF의 버전/페이지 오류를 수정하거나 숨기지 않는다.

수치 MD의 `criterion_source: permit_first`는 허가서를 또 검색하여 다른 기준을 고르는 기능이 아니다. 같은 시험에서 이미 확인한 기준 원문을 재사용한다. 매칭이 불명확하면 보류하며, SP 기준과 허가 기준의 문서상 불일치 검사는 실제 결과의 적합 여부와 별도로 유지한다.
판정 프롬프트만 바꿔서는 이런 추출 오류를 제대로 고칠 수 없다. 실제로 허가서의 이 문제를 발견해 추출기 회귀시험을 추가했다.

## 4. MD는 모두 같은 종류가 아니다

### 실행 규칙 MD: `sp_pdf_judger/rules/`

현재 `document.md`, `sky_covione.md`에 27개 규칙이 있다.
파일 첫 부분 `---` 사이의 `rules:` 목록이 실제 실행 대상이다.
ID, 제목, 대상(`selector`), 설명/의미 조건(`instruction`), 연산(`operation`), 설정(`params`)으로 구성된다.
그 아래 일반 설명 본문까지 자동으로 실행하는 것은 아니다.

- 결정적 연산: 날짜 계산, 수치 비교, 필수 시험 목록 등. Python은 범용 계산기 역할이고, 적용 대상과 설정값은 MD에 둔다.
- 의미 연산: `operation: semantic_review`이면 CLOVA가 `instruction` 문장을 읽고 근거를 판단한다.

따라서 “MD만 바꿔 고친다”는 것은 가능하지만 종류를 구별해야 한다.
기간 비교 연산의 기준을 28일에서 30일로 바꾸려면 해당 `params` 값을 고친다.
자연어 의미 규칙이면 `instruction`을 고친다. 설명 문장만 바꿔 놓고 숫자 설정은 그대로 두면 계산은 달라지지 않는다.
새로운 종류의 이미지나 표를 읽는 기능, 아직 없는 범용 연산 자체는 코드 보강이 필요할 수 있다.

실제 CLOVA 예제는 `tests/fixtures/semantic_proof/2`와 `4`이다.
동일한 세포농도 3.00×10^6에 대해 MD의 자연어 기준만 2.00×10^6 이상 / 4.00×10^6 이상으로 바꿨을 때 PASS / FAIL이 되는 것을 확인했다.
이는 엔진 검증 예제이지 운영 의약품 기준이 아니다.

공정 처리시간/첨부용제의 실행 예제는 `docs/examples/time_rules/rules.md`이다.
공정은 시작·종료일시 차이를 기재 처리시간과 비교하는 `elapsed_time`, 용제는 기존 `expiry` 연산을 사용한다.
이제 이 범위의 필드명·허용오차·유효일 계산 정책은 MD 설정만 바꿀 수 있다.
다만 원본 더미에는 예제 필드가 없으므로 기본 운영 규칙에 무조건 추가하지 않았으며,
실제 제품의 자료/허가 규약을 확인하고 적용 범위를 정해야 한다. 별도 PDF 3개의 성공을 모든 양식의 성공으로 해석하지 않는다.

### 기존 참고 디테일 MD: `sp_pdf_judger/domain_details/`

`overall.md`, `companies/*.md`, `products/*.md`는 공통·회사·제품별 참고 설명이다.
기존 일반 의미 판단 프롬프트의 배경자료로 쓰인다. 실행 규칙처럼 각각 독립된 결과와 근거를 보장하는 구조는 아니다.
현재 허가서 전용 ID 판정 프롬프트는 연결 허가서와 SP에 집중하므로 이 배경 문서 전체를 그대로 넣지 않는다.
**반드시 검출돼야 하는 추가 로직은 참고 MD에 문장만 덧붙이지 말고 실행 규칙으로 등록하고 시험해야 한다.**

나머지 `docs/*.md`와 `README.md`는 개발·운영 설명이다. 수정했다고 판정 로직이 바뀌지는 않는다.

## 5. 룰, RAG, LLM의 차이

룰은 “정해진 조건으로 계산”한다. `15 ng/mg 미만`에 결과가 `15`이면 경계값이므로 불충족이다.
날짜, 같은 단위의 숫자, 합계처럼 계산 가능한 것은 재현 가능한 코드로 검사하는 것이 중요하다.

RAG는 “관련 근거를 찾아주는 검색”이다. 검색 자체가 적합성을 판정하는 것은 아니다.
허가서 검색은 시험명뿐 아니라 제조단계도 사용한다. CHO 마스터 세포주의 시험과 CHO 제조용 세포주의 시험을 구분해야 한다.
현재 일반 참고자료 검색은 로컬 TF-IDF 계열이고, 허가서는 문단·시험명·단계의 일치 점수로 후보를 찾는다.
SP의 'DNA시험'과 허가서의 'DNA함량시험'처럼 이름이 다르면 실행 MD의 제품별 `permit_search_aliases`로 검색 후보를 연결한다. 원문을 고치거나 동일 시험이라고 확정하는 기능은 아니며, 제조단계와 실제 기준의 대조는 계속 필요하다.
외부 벡터DB를 설치해야만 가능한 구조는 아니다.

LLM은 “문장을 해석하고 어떤 기준이 해당하는지 연결”한다.
하지만 숫자 비교를 틀릴 수 있다. 실제 D05 시험에서 기준보다 낮은 세포농도와 생존율을 CLOVA가 합격으로 답했다.
그래서 모델의 합격을 곧바로 정답으로 간주하지 않고, 원문 연결 및 확정 가능한 수치 계산을 다시 검사한다.
다른 단위·여러 대상 등 모호한 연결을 임의로 계산해 합격시키지는 않는다.

## 6. 합격·불합격·보류를 구분해야 하는 이유

- 합격: 확인 가능한 기준과 결과가 충족됨.
- 불합격: 기준 위반 또는 필요한 충족 사실의 미달을 확인함.
- 보류: 필요한 결과가 없거나, 추출/근거 연결/모델 응답이 불완전하여 결정할 수 없음.
- N/A: MD 규칙의 대상 제품이 아님. 자료가 없다는 이유로 N/A를 쓰지 않음.

예를 들어 D00 원본19쪽에는 무균시험 결과란에도 `균이 확인되지 않아야 함`이라고 적혀 있다.
이는 실제로 균이 없었다는 관측 결과와 다르다. 원본 PDF를 육안 확인했으며, 시스템은 이 부분을 임의로 합격 보정하지 않는다.

검수 실행 오류가 나면 이전 CSV를 보여주지 않고 중단한다.
단, 같은 입력의 저장된 실패 결과는 실패 이력으로 열람할 수 있다. v93부터 서버 재시작 후에도
열람만으로 유료 재판정하지 않고, 기존 **검수 진행**을 눌러 명시적으로 재시도한다.
재시도 전 이전 pickle/CSV를 보존하며 정상 캐시(진짜 보류 포함)는 계속 재사용한다.
최종 결과를 저장하기 전 프로세스가 중단된 작업의 단계별 재개까지 완성한 것은 아니다.
세부 범위는 `CACHE_FAILURE_RECOVERY.md`를 본다.

v95부터 판정 이후 제조요약도 그래프를 만드는 작업도 화면 처리에서 분리했다.
준비 중 목록으로 나갔다 돌아와도 같은 입력의 작업을 이어서 기다리며, 완료 전에는 이전 결과나 가짜 최종 링크를 표시하지 않는다.
PDF를 읽는 알고리즘은 그대로이므로 첫 추출 시간 자체가 줄었다는 뜻은 아니다.
기존 동기 시뮬레이션 캐시 래퍼를 별도 작업 모듈로 대체했으며 서버 재시작 복구/내용 해시 보증까지 구현한 것은 아니다.
입력 동일성과 오류 처리, 실제 화면 검증의 범위는 [SIMULATION_PREPARATION.md](SIMULATION_PREPARATION.md)를 본다.
v96부터 PDF 읽기/구조 오류는 공정도 미발견과 구분해 중단하며, CSV 추정 구조를 표시할 때는 그 출처를 경고한다.
기존 구조 선택 규칙과 숫자는 유지한다. 예를 들어 D02는 PDF9노드와 판정용CSV10노드가 달라 CSV가 선택되는데,
이 표시용 연결선을 실제 PDF의 제조 순서가 검증됐다는 뜻으로 해석하면 안 된다. MD 공정 날짜 판정은 별도 엔진 결과다.

실행 MD의 오타·잘못된 값·중복 키도 `policy_schema.py`에서 먼저 검사하여 판정을 시작하지 않는다. `scripts/validate_rules.py`로 API 호출 없이 같은 설정 검사를 실행할 수 있다. 이 검사는 기준의 의학적 적절성을 보장하는 검사가 아니라, 작성한 옵션이 다른 뜻으로 실행되거나 무시되는 실수를 줄이기 위한 장치다.
정상 파일명, 모델의 높은 확신, “모든 조건 충족”이라는 문장만으로 통과시키지 않는다.

## 7. 테스트와 아직 남은 것

자동 테스트, 실제 PDF 오프라인 회귀, 실제 CLOVA 통합, 브라우저 UI 검증은 각각 다른 증거다.
자동 테스트가 통과했다고 LLM의 모든 답이 맞다는 뜻은 아니다.
회귀 실행은 규칙 ID뿐 아니라 일부 핵심 개별 시험 결과도 확인하며, 보류가 남은 live 실행은 수락 완료로 표시하지 않는다.
원본 파일은 고치지 않고 문서와 정답표의 모순을 별도로 기록한다.

아직 이미지 A/B/C의 모든 양식·제품·예외를 완성한 상태는 아니다.
범용 추출 QA, 수기서명, 모든 단계의 허가서 기반 필수 시험 자동 목록, 용제 만료일, 단계별·용기별 기준 등 추가 구현/검증이 남아 있다.
제조요약도 날짜·제조정보 카드는 현재 같은 MD 판정 결과를 재사용하며 UI에서 따로 판단하지 않는다. `report_group`으로 표시할 카드 그룹을 설정한다. 기존 일반시험법 등에는 아직 코드에 남은 판정 규칙이 있으므로, 모든 판단이 이미 MD로 완전히 이전됐다고 설명하면 안 된다.

최신 상태는 `WORK_STATUS.md`, 범위는 `VALIDATION_SCOPE.md`, 규칙 작성법은 `MD_RULES_GUIDE.md`를 본다.
실제 화면에서 확인한 동작과 아직 남은 UI 회귀는 `UI_VERIFICATION.md`에 구분했다.
