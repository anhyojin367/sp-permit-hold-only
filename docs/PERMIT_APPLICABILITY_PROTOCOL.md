# 조건부 시험 의무 응답 검증 (v78, 선택형 기반)

## 현재 하는 일 / 하지 않는 일

`permit_applicability.py`는 **이미 검토해 고정한 조건 설정**과 해당 단계·배치의 SP 사실을
LLM이 정확히 인용했는지 검증한다. 숫자는 Decimal 비교로 다시 계산한다. 문서 임의 조건을
자동으로 찾아 올바른 의무/절차로 분류하는 전체 기능은 아직 아니다. 운영27MD에는 적용하지 않았다.

예를 들어 합성 허가에 “100 mL 용기인 경우에만 아래 시험을 수행”과 “2차 이상일 때만 무균시험 수행”이
있으면, 두 조건 모두 해당 배치의 원문으로 확인해야 한다. 값이 없는 것은 조건이 거짓인 것과 다르다.
“농도에 따라 희석 생략”은 절차 조건이므로 그 사실만으로 함량시험을 면제하지 않는다.

## 고정 입력의 경계

- v77 원문 소유 목록이 오류 없이 연결되어야 한다. 검토 지문과 모든 문단ID(전역 안내 포함)를 확인한다.
- RequirementSpec은 말단 의무 문단, 실제 상위 제조단계, 연결할 SP 단계 및 all/any 조합을 고정한다.
- ConditionSpec은 직접 소유된 본문 구간ID, 수행 조건/절차 구분, 필드, 비교 연산, 값, 단위를 고정한다.
  자기 및 상위 문단의 조건을 자동으로 모두 포함한다. 임의 다른 단계/날짜 문단은 가져오지 않는다.
- **이 설정의 의미 해석이 원문과 맞다는 사실까지 ID 검사만으로 증명되지는 않는다.** 현재 합성 템플릿의
  해석을 명시적으로 검토한 시험이다. 실제 허가의 자연어→조건 설정 생성·검토와 MD 어댑터는 남았다.
- 지원 비교는 eq/ne/gt/gte/lt/lte와 유한한 십진수다. 단위는 일치해야 한다. 단위 환산을 추정하지 않는다.
- 현재 SP 사실 입력은 한 물리 페이지에 명시적인 `제조단계: ...`, `제조번호: ...`가 하나씩 있는 진단 양식이다.
  실제 SP의 다양한 표는 기존 단계/배치/원문 구간 검증과 연결하는 어댑터가 필요하다.
- 사실ID는 전체 SP 페이지 지문/파일/단계/배치/페이지/문자 위치/인용에 묶인다. 값 누락·중복·상충·미지원 표기,
  NaN, 단위 불일치는 unknown이다. 애매한 제조번호나 두 번째 헤더를 무시하여 기본 배치로 쓰지 않는다.

## 응답 수락 조건

1. 계약 지문 및 허가 전체 문단ID를 확인한다. 허가·조건 설정이 바뀐 오래된 응답을 수락하지 않는다.
2. 각 SP 단계·배치에 대응하는 전체 의무를 정확히 한 번 반환해야 한다.
3. 상위/자기 조건, 해당 조건에 대한 모든 사실 ID와 인용을 확인한다. 여러 값 중 하나만 선택하면 거부한다.
4. 조건별 truth는 코드의 독립 수치 대조와 같아야 한다. **최종 applicability는 모델 응답에서 받지 않는다.**
   근거 검증 통과 후 코드가 계산한다. 수행 조건에 unknown이 하나라도 있으면 unknown이다.
   모든 수행 조건이 확정되고 all/any 조합이 거짓일 때만 not_required로 계산한다.
5. procedure도 근거 응답에 포함하지만 시험 수행/면제 조합에는 사용하지 않는다.
6. 스키마 오류·누락·중복·인용 변조·잘못된 truth이면 응답을 거부하고 해당 묶음의 적용 여부는 unknown으로 남긴다.
   모델이 applicability 필드를 추가해도 거부한다. 모델의 자유서술 reason은 감사 원본에만 보존하며
   최종 판정 사유는 코드가 작성한다. 별도 `validate_response`는 완성된 결과의 최종 집계까지 엄격히 감사한다.

`required`는 시험이 필요하다는 뜻이지 시험결과 합격이 아니다. `not_required`도 전체 문서 합격이 아니다.
실제 시험 존재/누락·결과 적합 판정 연결은 별도 단계다. unknown을 정상 또는 면제로 집계하면 안 된다.

## CLOVA 입력 방식과 검증

모델에 ID 연결을 다시 추측시키지 않도록, 코드가 고정 근거 ID/원문 인용/조건별 해당 배치의 사실을
미리 연결한 반환 틀을 제공한다. 모델은 사용 가능한 관측값의 truth/reason만 채운다.
값 누락·중복·단위 불일치처럼 코드가 먼저 확인할 수 있는 근거 부족은 unknown으로 고정한다.
**사용 가능한 숫자의 참거짓 정답이나 최종 적용 결론은 프롬프트에 주지 않는다.** 검토된 조건식과
연결 근거만 명시한다. 응답 후 별도 검증기가 계산/근거를 대조하고 최종 결론을 만든다.
이는 “LLM이 시험 면제를 정확히 판단했다”는 증거가 아니라, 모델 응답의 근거 검증과 결정적 집계의 시험이다.
문서 내 지시문은 자료로 구분한다. 문서 임의 조건 해석을 지원하는 단계로 과장하지 않는다.

첫 실제5사례에서는 인용 축약/상위조건 누락/값이 없는데 수행 확정 등의 오류 응답을 모두 거부했다.
`.local_validation/applicability_proof/live-initial-failure.json`에 실패 이력을 보존했다.
두 번째5사례는2통과/3거부였으며 `live-bound-template-failure.json`에 보존했다.
세 번째는3통과/2거부였고 `live-observed-facts-failure.json`에 보존했다. 이 회차에서 조건별 숫자/근거는
전부 맞았지만 조건 미해당과 판단 불가의 최종 집계를 모델이 혼동했다. 이에 모델 응답에서 집계를 제거하고
검증된 근거를 바탕으로 코드만 종합하도록 역할을 분리했다. 잘못된 최종 집계를 무시해서 합격시키는 방식이
아니라 서로 다른 엄격한 응답 스키마다. 신규 실제5사례 검증 결과는 WORK_STATUS.md를 따른다.

근거 전용 첫 회차도3/5 통과였다(`live-evidence-first-pass-failure.json`). 숫자 자체의 오판이 남아
proof에서 최대1회만 재검토하는 절차를 추가했다. 첫 실패·후속 응답을 모두 보존하고, 정답 truth는
주지 않는다. API 예외는 이 계층에서 재시도하지 않는다. 재검토 후에도 틀리면 전체 묶음을 unknown으로 둔다.
후속 결과는 논리7요청/4사례 성공/복수배치1사례 거부다. 이는 안전 차단 확인이지 전체 API 수락이 아니다.
이후 아래 배치별 요청 분리로 혼입을 줄이는 방식을 검증했다. 운영 경로에는 적용하지 않았다.

proof의 `--isolate-targets` 선택지는 **검토된 단일 제조단계**에서 각 배치의 사실만 따로 전송한다.
각 응답에 그 배치의 전체 의무와 허가 전체 문단ID가 필요하다. 개별 검증 후 다시 전체 대상/의무 목록을
검증하므로 분리하면서 실패 배치를 누락할 수 없다. 하나라도 두 번 모두 거부되면 전체 묶음은 unknown이다.
이 선택지는 실험용 runner에만 있으며 제품 파이프라인에 연결된 재시도 정책이 아니다.

배치분리 실제 검증(46635)은 **5사례 모두 기대일치**로 종료했다. 기존 실패 이력은 삭제하지 않았다.
이는 합성 수치 계약의 한 실행이며 모든 자연어/임의 배치에 대한 정확도 보증은 아니다. 기존 실패 응답은
이후에도 반드시 거부되어야 한다. 운영 MD 연결, 실제 SP 표의 독립 사실 범위 검증은 여전히 남아 있다.

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_permit_applicability.py tests/test_permit_applicability_pdf.py
.\.venv\Scripts\python.exe scripts/prove_permit_applicability.py
.\.venv\Scripts\python.exe scripts/prove_permit_applicability.py --live
.\.venv\Scripts\python.exe scripts/prove_permit_applicability.py --live --isolate-targets --output .local_validation/applicability_isolated
```

별도6PDF/총7쪽에서 수행필요·수행조건불충족·사실누락·절차조건불충족·복수배치5사례를 검증한다.
원본 사용자 문서는 수정하지 않는다. live는 승인된 CLOVA 비용이 발생하며 논리 요청에는 응답캐시가 포함될 수 있다.
이 테스트의 성공은 모든 자연어 허가·모든 실제 SP 양식·전체 A/B/C 검증 완료를 뜻하지 않는다.

v79에서 검토된 조건 설정의 선택형 MD 로더/전체 파일 지문과 실제 합성PDF 연결을 추가했다.

아니다. 실제 SP 표/필수시험 존재/기존 카드 연결 및 자연어 조건의 초안·검토는 여전히 필요하다.

아직 필요하다. 한 본문에 여러 조건이 섞인 경우의 문장 구간ID 확장도 필요하다.
운영 활성화 전에는 부분 지원 범위를 명확히 보류해야 한다.
