# 판정 통신 실패와 캐시 재사용

## v99: 같은 제출 건의 프로세스 간 중복 실행 차단

`ReviewJobs`는 여전히 한 프로세스 안의 작업을 관리한다. 별도 서버 프로세스와의 충돌은
새 `sp_process_lock.py`가 맡는다. `ensure_judgement_artifacts()`의 작업 스레드는
같은 캐시 키의 잠금을 얻은 뒤 **디스크 재확인 → 판정 → 결과 파일 발행 → 상태 기록**을 수행한다.
디스크 작업 본문은 `_ensure_disk_artifacts()`로 분리했고 판정 로직/캐시 버전은 그대로다.

- 잠금 파일은 임시 캐시 상위의 `.locks/<입력키>.lock`이다. 결과/실패 보존 폴더 밖에 두고 지우거나 교체하지 않는다.
  빈 파일이 남아 있는 것은 실행 중이라는 뜻이 아니다. 실제 소유 여부는 운영체제가 관리한다.
- 다른 프로세스가 같은 입력을 처리 중이면 기존 진행 문구 영역에 대기를 알린다. 그 요청은
  앞선 시도가 저장한 정상 결과 또는 실패 이력을 읽으며, 실패했더라도 새 유료 재시도를 연이어 시작하지 않는다.
  대기 중 눌린 재시도 의사는 다음 시도로 넘기지 않는다. 별도로 다시 누른 명시적 재시도는 기존 방식대로 동작한다.
- 앞선 프로세스가 결과를 발행하지 못하고 끝났으면 이미 기다리던 요청도 오류로 멈춘다.
  중복 판정을 자동 시작하지 않는다. 잠금 대기 기본 상한은30분이며 시간 초과도 잠금을 우회하지 않는다.
  대기 자체는 작업 스레드에서 이루어지고 기존 목록/진행 화면 코드는 바꾸지 않았다.
- 잠금을 얻은 뒤 입력 키를 다시 계산한다. 대기 중 PDF/허가 파일 식별값이나 MD 지문 등이 바뀌면
  이전 결과를 적용하지 않는다. 기존 크기·수정시각 기반 파일 식별을 내용 해시로 바꾼 것은 아니다.
- 서로 다른 입력 키는 이 잠금을 공유하지 않는다. 다만 동일 프로세스의 기존 단일 작업 큐는 유지된다.
  공유 상태 인덱스의 서로 다른 문서 동시 쓰기는 아직 별도의 보호가 필요하다.
- 새 코드의 Windows 실제 프로세스 시험에서 소유 프로세스 종료 후 잠금 해제를 확인한다.
  Windows 가상환경 런처만 죽이는 잘못된 시험을 피하도록 실제 인터프리터 PID를 확인한 뒤
  **시험이 생성한 자식 프로세스만** 종료한다. 사용자 앱/검수 서버에 종료를 주입하지 않는다.

재현: `python -m pytest tests/test_review_process_lock.py tests/test_process_lock_boundaries.py -q`.
신규20검사는 실제 별도 프로세스8개 사례와 경계12개 사례이며 모두 합성 판정/API0이다.
최초7검사는6실패/1통과였고, 보완 후 기존 실패 보존/재시도/Streamlit 검사까지 관련69개가 통과했다.
전체시험과 실제 정상 D02 화면의 최종 상태는 `WORK_STATUS.md`를 따른다. 새 유료 D00~D12 판정이 아니다.

**제한:** 협력하는 동일 코드/동일 로컬 캐시 위치의 프로세스끼리만 보호한다. 잠금을 사용하지 않는 구버전,
직접 CLI 실행, 다른 컴퓨터/캐시 경로, 네트워크 파일시스템의 잠금 보장은 포함하지 않는다.
프로세스가 죽기 전에 시작한 원격 API 요청의 서버 측 완료/청구 취소도 보장하지 않는다.
종료 후 새 요청이 최종 캐시 없는 폴더를 만나면 여전히 처음부터 실행할 수 있으므로,
중단 상태 영속화·단계 체크포인트/명시적 재개 정책은 다음 작업이다. 단계별 복구 완료가 아니다.

구현에 사용한 표준 API 동작은 Python 공식 문서의
[Windows `msvcrt.locking`](https://docs.python.org/3/library/msvcrt.html#msvcrt.locking),
[Unix `fcntl.flock`](https://docs.python.org/3/library/fcntl.html#fcntl.flock)을 참고했다.
실행 검증은 현재 Windows 환경이며 Unix 분기의 실제 OS 시험은 하지 않았다.

## 기존 실패 이력과 명시적 재시도

v76은 시험 결과의 보류와 API 실행 실패를 구분한다. v93은 저장된 실패 결과를
서버 재시작 후 열람할 때도 자동 유료 재호출하지 않도록 보완한다. 화면 HTML/CSS와 버튼은 바꾸지 않는다.

- 실제 근거 부족으로 HOLD가 나온 정상 응답은 캐시 재사용이 가능하다.
- before/after 중 하나라도 `llm_last_error`가 있거나 논리 요청 수보다 성공 수가 적으면 실행 실패로 본다.
- 실행 실패 결과는 status index에 `failed`로 기록하며 **완료된 검수 결과로는 재사용하지 않는다**.
  다만 세션이 없어도 같은 입력 키의 디스크 결과를 **실패 이력 열람용**으로 반환한다. 판정 상태나 실패 근거를 합격으로 바꾸지 않는다.
- 현재 실패 시도의 세션도 상세 확인을 위해 유지한다. 페이지를 여는 것만으로 반복 API 호출하지 않는다.
- 사용자가 같은 문서의 **검수 진행**을 새로 누르면 그 문서의 실패 세션/완료된 실패 작업만 해제한다.
  UI 세션에 선택 문서의 경로·크기·수정시각에 결합된 일회용 재시도 의사를 보관하고, 다음 작업 조회 시 소비한다.
  실행 중인 작업은 중복 실행하지 않고 정상 캐시(진짜 보류 포함)는 그대로 재사용한다. 작업 스레드는 세션에 접근하지 않는다.
- 읽을 수 없는 pickle/잘못된 형식/버전 불일치도 조용히 새 실행으로 넘어가지 않는다.
  기존 오류 표시 경로에서 문서 목록의 **검수 진행**으로 재시도하도록 안내한다.
- 명시적 재시도 전 `<캐시키>.failed-<고유번호>` 형제 폴더에 기존 작업 폴더 전체를 복사한다.
  기존 pickle 바이트, 요약 CSV, 단계별 CSV가 보존된다. 보존에 실패하면 새 추출/API 전에 중단한다.
  보존본 pickle 안의 절대경로는 당시 원래 위치이므로 보존 폴더가 곧바로 실행 가능한 새 캐시라는 뜻은 아니다.
- 새 pickle은 같은 폴더의 임시 파일에 완전히 기록한 뒤 원자적으로 교체한다. 직전 파일을 먼저 비우지 않는다.
  저장 오류는 숨기지 않으며, 성공적으로 캐시를 발행한 다음에만 status index를 갱신한다.
  저장된 결과의 후처리 오류도 새 유료 실행으로 전환하지 않는다.
- 판정 내용/스키마는 같아서 캐시 버전은 v85를 유지한다. 버전 증가 때문에 모든 정상 문서가 다시 유료 실행되는 일을 피한다.

## v93 검증과 남은 범위

`python -m pytest tests/test_review_retry_recovery.py tests/test_failed_judgement_cache.py tests/test_submission_cache.py tests/test_review_jobs.py -q`.
추가로 시뮬레이션/미완료 시험 카드/표시 상태 권한 검사를 합친 관련72검사가 통과했다.
최초 실패14개를 확인한 뒤 수정했다. 최신 전체 시험 수는 `WORK_STATUS.md`를 따른다.

`.local_validation/prove_retry_v93.py`는 새 격리 폴더에 합성 실패 캐시를 만들고 서로 다른4개
Python 프로세스에서 `실패 열람 → 실패 재열람 → 명시적 재시도 → 성공 재열람`을 실행한다.
각 모의 판정 실행 횟수는0/0/1/0이며 실제 API는0이다. 이전 pickle/CSV의 보존도 검증한다.
결과는 `.local_validation/retry_v93/proof.json`에 있다. 모의 성공을 CLOVA 성공이나 브라우저 검수로 세지 않는다.

v94에서는 `tests/test_review_retry_streamlit.py`의 실제 Streamlit AppTest로 기존 목록 복귀/검수 진행
버튼과 rerun 연결까지4개 사례(실패/손상/정상/재실패)를 확인했다. 참조 조회·시뮬레이션 본문·판정기는
격리 fixture이고 실제 API0이다. v93이 적용된 개발 서버의 실제 D02 정상 캐시 열람 경로도 별도로 확인했다.
실제 실패 문서의 유료 재시도 성공이나 중단 작업 복구를 증명한 검사는 아니다.
새 브라우저 세션이 전역 화면 데이터 캐시를 불필요하게 지우지 않도록 한 별도 성능 수정은
`UI_VERIFICATION.md`의 v94를 참고한다. 실패 캐시를 정상으로 인정하거나 입력 변경 검사를 생략하지 않는다.

**아직 완료하지 않은 것:** API 도중 프로세스가 죽어 최종 pickle이 없는 작업의 단계별 재개,
모든 산출물/상태 인덱스를 한 번에 저장하는 트랜잭션,
재시도 중간에 다시 죽은 경우의 완전 복구, 장기 백업 정리 정책이다.
기존 경로·크기·수정시각 방식의 입력 키도 이번에 내용 해시 방식으로 바꾼 것은 아니다.
저장 이력 보호가 LLM 판단 정확도나 전체 A/B/C 수락 완료를 뜻하지 않는다.
v99의 동일 입력 파일 잠금은 위 별도 절에서 보완했지만 이 나머지 한계를 해결한 것은 아니다.

v76의 기존12개 검사는 before/after 오류, 성공수 부족, 진짜 보류, 문서별 명시적 재시도,
status 기록, 현재 실패 결과 열람을 다룬다. 그중 디스크 실패 시 자동 재생성을 기대하던
1개는 v93에서 실패 이력을 유료 재호출 없이 열람하는 기대값으로 바꿨다.

## 이번 UI 검증의 환경 실패

v75 기본 샌드박스 개발 서버에서 CLOVA 연결이 차단되어 before2요청/0성공,
after202요청/0성공과 `Connection error.`가 기록됐다. 이 결과는 UI 성공으로 세지 않는다.
실패 artifact는 `c7682d8c55518701987cd3ef`로 보존한다.
네트워크 허용 환경의 `scripts/check_clova.py`는 실제 HCX-007 응답을 파싱했다.
복구 서버는 127.0.0.1만 바인딩하며 명시적인 검증용 `CLOVA_RESPONSE_CACHE_DIR`를 사용한다.
검증 캐시를 포함한 논리 요청 성공 수를 신규 유료 호출 수로 해석하지 않는다.

샌드박스 네트워크 실패를 고치기 위해 TLS 검증, 방화벽, 보안 설정을 끄지 않는다.
승인된 API 호출에 필요한 실행 권한만 사용하고 키는 출력하지 않는다.
