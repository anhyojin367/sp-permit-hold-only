# MD 규칙 운영 안내 (개발 검증 중)

2026-10-01 새 요구사항 82개와 조수의 배포 검토 반영은 [v107 설명](FEEDBACK_20261001.md)을 참고한다.
`rules/requirements.md`는 삭제 없이 보존한 요구사항/구현 범위 목록이며 실행 규칙의 판정 수에 더하지 않는다.
새 목록 번호와 기존 R 번호는 다르므로 `aliases`와 `rule_ids`로 연결한다.

2026-09-29 사용자 제보에 따른 R29/R30 및 `result_aliases`(정확한 범위의 결과 표기 사전)는
`FEEDBACK_20260929.md`를 참고한다. 현재 운영 규칙은 29개이며, 아래의 운영27규칙 언급은 이전 버전 설명이다.

제공 허가의 실제 적용 범위 검토와 미승인 원문 검토 목록 생성은 `PROVIDED_PERMIT_REVIEW.md`를
참고한다. 이 검토 목록은 실행 규칙이 아니며, PDF 일부를 전부 읽었다고 전체 허가조건까지 승인하지 않는다.

v82의 조건 MD→필수시험 존재 검사 선택형 연결은 `CONDITIONAL_TEST_PRESENCE.md`와
`docs/examples/conditional_presence_rules/`를 참고한다. 조건 companion은 `_conditions/`에 두고
`permit_conditional_tests`에서 명시적으로 연결한다. 기존 운영27규칙과 무조건 필수시험 의미는 유지한다.

허가 필수시험의 배치 정보가 콜론 없는 표/인접 줄 형식이면 `BATCH_FIELD_LINKING.md`를 참고한다.
해당 선택형 연산과 예제는 운영27규칙에 아직 포함되지 않는다.

검토된 허가의 수치 조건을 별도 MD에서 읽는 선택형 로더는 `PERMIT_APPLICABILITY_MD.md`를 참고한다.
해당 예제의 루트는 `applicability`이며 위 운영 `rules` 디렉터리에 복사해 자동 활성화하는 파일이 아니다.
v80의 명시적 `reviewed_numeric_v1` 방식은 검토된 수치 조건을 API 없이 실행한다. LLM 실패를 자동으로
덮어쓰는 fallback이 아니며 원문/MD/단위/배치 검증과 근거 부족 보류는 유지한다.
임의 SP 표/실제 제품 운영 적용은 미완료다. 자연어 의미 규칙과 수치 조건 설정의 차이는 아래를 따른다.
v81의 정확한 절/단일 배치 표 연결은 `SCOPED_CONDITION_FACTS.md`에서 설명한다. 합성8사례와 제공
D00의 제조량 사실 연결을 검증한 선택형 입력이다. v82는 이 입력을 조건부 존재 판정과 기존 카드에
연결했지만 합성7사례의 선택형 검증이며, 실제 제품의 운영 규칙을 활성화한 것은 아니다.

## 무엇을 고치면 무엇이 바뀌는가

실행 규칙은 `sp_pdf_judger/rules/document.md`, `sky_covione.md`에 있다.
각 파일 맨 위 `---` 사이 YAML의 `rules` 목록과 선택적인 `permit_search_aliases`, `result_aliases`, `requirements` 목록을 읽는다. 아래 설명 본문은 운영 문서이며 실행 조건이 아니다.
MD 변경 내용의 해시를 판정 결과에 저장한다. MD 또는 연결된 허가서가 바뀌면 이전 결과를 재사용하지 않는다.

규칙은 두 종류다.

1. 정확한 계산·비교: `operation`으로 범용 연산을 선택하고 `params`로 기준을 설정한다. 날짜, 경계값, 합계 같은 작업을 LLM 계산에 맡기지 않는다. 이 경우 설명 문장만 바꾸지 말고 해당 `params`도 바꿔야 한다.
2. 자연어 의미 판단: `operation: semantic_review`와 `instruction`을 사용한다. **이 유형은 instruction 문장을 바꾸면 CLOVA가 변경된 문장을 읽고 판단한다.** 추출된 근거가 없거나 API가 실패하면 보류다.

새로운 종류의 입력을 추출해야 할 때(예: 기존 추출기가 읽지 못하는 수기서명/이미지)는 MD만으로 해결되지 않는다. 추출기나 공통 연산 기능을 먼저 보강해야 한다.

## MD를 고친 직후 확인할 것

판정 전에 다음 명령으로 설정만 검사할 수 있다. PDF를 읽거나 CLOVA를 호출하지 않으므로 API 비용은 없다.

```powershell
.\.venv\Scripts\python.exe scripts/validate_rules.py
.\.venv\Scripts\python.exe scripts/validate_rules.py --rules-dir tests/fixtures/semantic_proof/2
.\.venv\Scripts\python.exe scripts/validate_rules.py --describe duration
```

첫 명령은 현재 운영 규칙 전체, 둘째는 지정한 폴더, 셋째는 한 연산에서 사용할 수 있는 `params` 이름·형식·필수 항목을 보여준다. 정상 종료코드는0, 설정 오류는2다. 실제 검수 파이프라인도 같은 검사를 PDF 추출/판정 전에 수행한다.

- `allow_same_day: false`와 `inclusive: false`는 불리언이다. 따옴표를 붙인 `"false"`는 문자열이므로 거부한다. 이전에는 문자열이 참처럼 처리되거나 실행 오류로 뒤늦게 발견될 수 있었다.
- `minimum_days: 28`은0 이상의 정수다. `"28"`, `true`, 음수, 소수는 임의 변환하지 않는다.
- `tests: ['무균시험']`처럼 목록을 사용한다. 문자열 하나나 빈 목록, 공백뿐인 이름, 같은 이름을 중복 기재하면 거부한다.
- `allow_same_dya`, `permit_search_aliaes`처럼 잘못 쓴 이름과 YAML의 같은 키 중복을 거부한다. 뒤에 적은 값으로 앞의 기준을 조용히 덮지 않는다.
- 허가 문구 추출 정규식에는 비교할 부분을 괄호로 묶은 캡처 그룹이 필요하다. 문법이 틀리거나 빈 문자열에도 맞는 패턴, 허가/SP 두 패턴의 캡처 개수가 다른 설정을 거부한다.
- 같은 필드를 제조일과 유효일 양쪽으로 지정하거나, 합계 계산의 시작/종료 제목을 동일하게 지정하는 실수도 거부한다.

오류에는 MD 파일명과 해당 규칙 ID/설정 경로가 포함된다. 이를 해결한 뒤 정상·오류·경계·누락 사례를 재시험한다. **설정 검사 통과는 판정 기준의 적절성이나 새 문서의 정확성을 검증한 것이 아니다.** 설명 문장만 바꿔도 결정적 연산의 `params`가 자동으로 수정되지는 않는다.

## 자연어 규칙 예시

다음은 형식 예시이며 현재 활성 규칙이 아니다.

```yaml
---
rules:
  - id: CUSTOM-001
    title: 배양 상태의 복합 조건
    operation: semantic_review
    instruction: >-
      시험기준에 적힌 모든 조건을 시험결과와 각각 비교한다.
      세포가 뭉치지 않는 것과 구형인 것 중 하나만 확인되면 합격으로 처리하지 않는다.
      명시적으로 반대되는 결과는 FAIL, 필요한 결과가 빠져 있으면 HOLD이다.
    selector:
      type: test
      context: [CHO 마스터 세포주]
      test: 세포형태확인시험
---
```

- `id`: 중복되지 않는 추적용 식별자.
- `products`: 생략하면 공통 규칙. 기재하면 일치하는 제품에만 적용.
- `selector`: 추출 레코드 유형·제조단계·시험명으로 근거 범위를 지정. 파일명으로 판정하지 않음.
- `aliases`: 원래 A/B/C 요구사항과의 추적용 연결. 별칭이 있다고 그 요구사항 전체가 구현됐다는 뜻은 아님.
- `instruction`: 의미 판단용 조건 또는 결정적 규칙의 설명.
- `params`: 결정적 비교기의 실제 설정값.
- `report_group`: `manufacturing_dates`이면 기존 제조요약도 날짜 카드, `manufacturing_info`이면 제조정보 카드에 같은 MD 결과를 표시한다. UI는 별도 조건으로 재판정하지 않는다.
- `criterion_source`: 수치 연산 `numeric_compare`, `minimum_count`, `labelled_numeric_compare`의 기준 출처. `sp`(기본값)는 문서 자체 기준, `permit_first`는 개별 시험 판정에서 이미 원문 연결이 검증된 허가 기준을 재사용한다. 다른 연산에 지정하면 무시하지 않고 설정 오류로 거부한다.

## 허가서와 RAG

업로드 시 연결한 허가서는 해당 제출 건에만 적용한다. 기존 SP에서 허가서를 교체하면 이전 파일은 이력으로 보관하고 현재 연결만 바꾼다.
명시적 연결이 있으면 기본 제품 카탈로그의 다른 허가서를 섞지 않는다. 허가서 없는 기존 카탈로그 경로는 유지한다.
전역 검색 자료에서 제품별 허가서를 무차별 검색하던 경로는 제외했다.
시험명뿐 아니라 제조단계·시험대상을 대조한다. 허가서 원문에서 확인되지 않는 LLM 근거는 판정에 채택하지 않는다.
허가서 부재·여러 기준의 충돌·근거 추출 실패는 합격으로 덮지 않는다.
LLM은 후보·문장 ID를 선택하고, 원문은 코드가 해당 자료에서 직접 연결한다. 선택한 문장을 빠뜨리거나 중복하면 보류다.
방법만 있고 결과 허용 기준이 없는 허가 항목은 원문 검증 후 SP 기준을 적용한다. 실제 결과값이 없는 경우와 혼동하지 않는다.
숫자 비교는 모델이 합격이라고 해도 별도 계산으로 재확인한다. 확정 가능한 수치 위반을 발견하면 합격으로 두지 않는다.

R07/R08/R28은 `criterion_source: permit_first`로 설정했다. 예를 들어 SP는 5 ng/mL 이하, 허가서는 10 ng/mL 이하, 실제 결과는 8 ng/mL이면 **허가 기준에 대한 결과 비교**는 합격할 수 있다. **SP에 적힌 기준이 허가서와 다르다는 문서 문제**는 별도 `permit_test` 규칙으로 확인한다. 두 질문을 같은 실패로 섞지 않는다.

- 연결된 허가서의 결과 기준이 원문으로 확인되면 그 기준을 사용한다. 추가 LLM 호출로 새로운 기준을 선택하지 않는다.
- 허가서 해당 시험이 없거나 시험방법만 있다는 것이 확인된 경우에만 SP 기준으로 돌아간다.
- 허가서 추출/API/원문 연결 실패, 서로 다른 표 행에서 선택된 기준의 충돌은 보류다. 다른 레코드의 기준을 빌리거나 지난 판정의 기준을 재사용하지 않는다.
- R28의 `sp_supplement_if_no_numeric_limit: true`는 허가서가 수치 없이 시험법만 참조할 때 SP의 수치·측정대상을 보완 검사하는 명시적 예외다. 해석하지 못한 숫자나 한도 표현이 있으면 '기준 없음'으로 취급하지 않는다. 인식되지 않는 USP 조문 번호 등도 자동 추측하지 않고 확인 대상으로 남길 수 있다.

실제 선택된 `source`, `criteria`, `reason`, 원문·페이지는 결과 JSON의 `comparison_bases`와 각 MD finding의 같은 이름 필드에 기록한다. 이 메타데이터는 코드가 검증한 자료에서 만들며 LLM이 파일 경로나 페이지를 생성하지 않는다.

근거 링크의 쪽수는 업로드한 PDF 파일의 **물리적 페이지 순서(1부터)**다. 원문에 인쇄된 쪽번호와 다를 수 있다. 예를 들어 제공 허가서의 DNA 기준은 파일13·14쪽에 있고, 원문 하단에는 각각 `15/60`, `16/60`도 표시되어 있다. 링크와 인쇄 번호를 혼동해 다른 페이지를 고르지 않는다.

## 시험명이 다르게 적힌 허가서를 찾는 방법

`rules`와 같은 깊이의 `permit_search_aliases`를 수정한다. 제품 범위와 원문상 연결 근거를 반드시 적는다.

```yaml
permit_search_aliases:
  - products: [스카이코비원멀티주]
    names: [잔류 숙주세포 유래 DNA시험, 잔류 숙주세포 유래 DNA함량시험]
    reason: 제공 SP와 허가서의 잔류 DNA 측정 명칭 차이
```

이는 **검색 후보를 추가**하는 설정이다. 두 시험이 같거나 결과가 적합하다고 자동 인정하지 않는다.
원문 제목과 실제 기준은 변경하지 않고 CLOVA가 단계·시험·조건을 대조한다. 같은 단계에 충돌하는 후보가 여러 개면 모두 남긴다.
특정 제조단계에 시험이 없을 때 다른 단계의 같은 이름 기준을 가져오지 않는 제한도 유지된다.
다른 제품에는 적용하지 않으며, MD에서 삭제한 설정은 다음 판정 때 제거된다. 실제 적용 목록은 결과의 `metadata.permit_search_aliases`에 기록된다.
`aliases: [A.1, B.2]`는 요구사항 추적 번호이므로 이 검색 명칭 설정과 다르다.

제공 SP의 '소/돼지유래플라스마부정시험'과 허가서 '소/돼지유래바이러스부정시험'은 제목 자체가 다르다. SP 기준문에 바이러스 오염 부정이 기재되어 후보로만 연결했다. 명칭 오류가 없다고 보장하거나 원문을 자동 교정한 것이 아니다.

## 판정과 검증

결과에는 규칙 ID, 상태, 이유, 원문/페이지, 규칙 해시가 남는다. PASS/FAIL/HOLD/N/A를 구분한다.
N/A는 대상 제품이 다른 경우이고, 필요한 자료가 없다는 이유로 PASS를 만들지 않는다.
현재 실행 규칙 27개는 제공 더미의 지정 오류와 제조일/시험일, 저장기간, 중복 추출, 동일 제조번호 일관성, 측정대상별 전체 결과 확인을 중심으로 구현했다. 이미지 A/B/C의 모든 세부 요구사항 구현 완료를 뜻하지 않는다.
R28은 `labelled_numeric_compare`를 사용한다. `params.expected_labels`의 대상이 모두 있어야 하며 한도값은 위 출처 정책으로 선택된 기준의 같은 대상에서 읽는다. 같은 단위라는 이유만으로 다른 크기의 입자 결과를 대신 비교하지 않는다. 이 연산의 누락/위반은 개별 시험의 모델 합격도 차단하고 앞선 응답을 audit에 남긴다.
기간·유효일·서명 순서 연산은 selector로 선택된 **모든 항목**의 날짜 근거를 요구한다. 하나만 유효하고 나머지 날짜가 비어 있거나 잘못되어 있으면 전체 합격이 아니다. 날짜가 없는 항목은 `incomplete_evidence`에 남는다. 다른 항목에서 이미 확인한 위반이 있으면 FAIL을 유지하고, 위반을 확정하지 못했지만 근거가 부족하면 HOLD이다. 날짜 전용 필드에 알 수 없는 주석/시각 형식이 있으면 임의로 무시하지 않는다.
저장기간도 같은 누락 원칙을 적용한다. 최소 개수 연산은 기준에 열거된 모든 측정대상의 결과와 단위를 요구한다. Z/B/P 중 Q를 대신 세거나 결과 단위를 생략한 수치를 합격 개수에 넣지 않는다. MD 검사와 개별 시험의 수치 방어기는 같은 계산기를 사용한다.
`expiry`의 `params.end_policy`는 `not_after`(계산일 이내, 기본) 또는 `exact`(계산일과 일치)이다. 현재 R11은 기존 조건을 유지하여 `not_after`를 명시했다. 어느 경우든 유효일이 제조일보다 앞서면 불충족이다. 월 계산은 고정 30일이 아닌 달력 기준이며 다음 월에 같은 일이 없으면 말일이다(2024.1.31 + 1개월 = 2024.2.29). 특정 허가서에서 전날 종료 등의 별도 규약을 요구하면 현재 연산이 지원한다고 간주하지 않는다.
유효·저장기간은 `12개월` 또는 `제조일로부터 12개월`처럼 온전한 0 이상의 정수 개월 표현을 읽는다. `1.5개월`, `12~18개월`, `12개월 또는 미정`, 날짜 연산 범위를 벗어나는 수치는 일부 숫자만 골라 사용하지 않고 보류한다. 같은 날짜/기간 필드가 한 레코드에 두 번 있으면 첫 값으로 결정하지 않는다. `storage_period`는 `period_field`, `start_field`, `duration_field`의 세 필드를 요구한다(기본값: 저장기간, 제조년월일, 허가된 저장기간). 누락된 허가 한도를 선택 사항으로 조용히 건너뛰지 않는다.
`test_after_manufacture`도 해당 단계의 모든 제조일 원문과 모든 시험 날짜를 확인한다. 제조일 후보가 일부 불완전하거나 서로 다르면 어느 배치의 날짜인지 추측하지 않고 보류한다. 시험기간 일부가 미정인 경우도 합격하지 않는다. 다른 시험의 입증된 날짜 위반은 유지하고 누락 근거·보류 카드도 별도로 남긴다. 이는 시각/시간대나 다중 배치의 자동 연결을 지원한다는 뜻은 아니다.
저장기한 대비 제조·시험일, 공정 선후, 허가 필드·시험 대조에도 일부 누락을 기록한다. 제목 행은 제조·시험 데이터가 아니므로 날짜를 요구하지 않지만, 실제 데이터 행의 날짜가 빠지면 건너뛰어 합격시키지 않는다. 이미 확인한 다른 항목의 불일치도 유지한다.
직접 투입량 합계는 MD에 지정한 `start_marker`~`end_marker` 안의 모든 성분 행을 읽는다. 행의 수량/단위가 불완전하거나 경계가 사라지면 보류다. 하위 완충액 조성은 중복 합산하지 않는다. 수량 열 제목은 기본 `분량`이며 필요한 경우 `params.amount_header`로 바꾼다.
지원되는 수치 형식의 소수점 검사는 `8.0 미만`이나 `≤8.0` 같은 단위 없는 기준도 포함한다. 기준1자리/결과7.66의2자리는 불일치다. 이는 숫자가 범위 안인지와 별도 검사이며, 유효숫자 전반이나 임의 반올림 정책을 구현했다는 뜻은 아니다.
특히 양식 학습 비교, 범용 표 추출 품질 보증, 수기서명 인식, 모든 시험의 단계별 기준 선택은 추가 검증 대상이다.

## 공정 처리시간(C.3)과 첨부용제 유효일(C.10)

`docs/examples/time_rules/rules.md`는 실행 가능한 별도 예제다. 기본 운영27개에는 포함되지 않는다.
제공 더미에 예제의 공정시각/첨부용제 필드가 없기 때문에 대상이 없다는 이유로 합격시킨 것이 아니다.
해당 제품에 적용할 때 운영 MD의 `rules` 목록에 복사하고 `products`, `selector`, 필드명을 맞춘다.
API의 `DocumentJudgePipeline(rule_dir=...)`는 별도 규칙 폴더를 받을 수 있으며 이 값은 기본 규칙에 추가가 아니라 **대체**이므로 운영 규칙을 누락하지 않는다.

- C.3은 새 `operation: elapsed_time`을 사용한다. `start_field`, `end_field`, `duration_field`가 필수이고 `tolerance_seconds: 0`은 정확히 같은 시간만 허용한다. 허용오차 변경은 MD에서 하지만 실제 허가/업무 기준에 근거해야 한다.
- `2026.09.25 23:45`~`2026.09.26 01:15`는5400초다. 기재 `1시간 30분`, `90분`, `1.5시간`, `5400초`가 모두 동일하며89분이면60초 차이로 불충족이다.
- `YYYY.MM.DD HH:MM[:SS]`, `/` 또는 `-` 구분 날짜, ISO의`T`구분, `YYYY년 M월 D일 H시 M분 [S초]`를 지원한다. 날짜 없는`09:00`, 일자만 있는 값, 잘못된 달력/시각, 중복 필드, 미정/일부 누락은 보류다. 다음날·자정·시간대를 추측하지 않는다.
- 처리시간은 일/시간/분/초 또는d/h/min/s이며 일은24시간이다. 개월은 시간으로 환산하지 않는다. 단위 없는90, 약90분,1~2시간,음수,순서가 뒤섞인 복합단위,1시간90분 같은 비정규 복합값은 보류다. 소수는 마지막 단위에만 허용한다.
- timezone/UTC오프셋/DST(서머타임)는 미지원이다. 현재는 시간대 없는 같은 지역 시계 기준의 기록만 비교한다. 종료가 시작보다 빠르면, 기재 처리시간이 누락돼도 입증된 역전은 불충족으로 남긴다.
- C.10은 별도 계산기를 만들지 않고 기존 `expiry`에 첨부용제 전용selector/필드와`end_policy: exact`를 설정한다. 완제품 제조일과 섞지 않고1월31일+1개월의 윤년 말일도 확인한다. `exact`는 예제 계약이며 모든 제품의 허가 규정이라는 뜻이 아니다.

재현(유료 API 호출 없음):

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe scripts/validate_rules.py --rules-dir docs/examples/time_rules
.\.venv\Scripts\python.exe scripts/validate_rules.py --describe elapsed_time
.\.venv\Scripts\python.exe scripts/prove_time_policies.py
.\.venv\Scripts\python.exe -m pytest tests/test_policy_elapsed_time.py tests/test_time_policy_pdf.py -q
```

스크립트는 `.local_validation/time_policy_proof/`에 별도 3개 PDF와 추출 JSON/보고서를 만든다. 제공 더미를 고치지 않는다.
Windows 기본 맑은 고딕을 사용하며 다른 환경은 `--font`에 설치된 한글 TrueType 파일을 지정한다. PDF pytest는 ReportLab/해당 폰트가 없으면 skip이므로 반드시 실행 여부를 확인한다.
이는 단순한 한 양식에서 추출 → MD 경로를 검증한 것이며, 임의 표/스캔본/모든 허가서로 일반화되었다는 뜻은 아니다.

허가서 문장 ID/유형/상태 형식 오류도 정답과 구분한다. 예를 들어 procedure에 PASS를 붙이는 응답은 채택하지 않고,
정확한 계약 오류를 알려 딱 1회 수정 요청한다. 다시 틀리면 보류이며, 실제 불충족/관측값 누락을 합격시키기 위한 재요청은 하지 않는다.
UI에는 코드가 만든 진단만 표시하며 모델이 반환한 API 오류/비밀정보 같은 문자열을 그대로 노출하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe scripts/validate_corpus.py
.\.venv\Scripts\python.exe scripts/validate_corpus.py --live --cases D00
.\.venv\Scripts\python.exe scripts/prove_md_semantic.py
.\.venv\Scripts\python.exe -m streamlit run sp_app.py --server.address 127.0.0.1
```

오프라인 시험과 실제 CLOVA 시험은 다르다. `--live`는 API 사용료가 발생하며 `.local_validation`에 결과를 저장한다.
실제 CLOVA 시험에서 동일한 요청은 검증된 응답 캐시를 쓸 수 있다. 오류 응답은 저장하지 않으며, 모델·프롬프트·규칙 변경은 캐시를 무효화한다.
응답 캐시가 검증되었다는 말은 JSON 형식 검증을 뜻하며, 판정 내용의 정답을 보장하지 않는다. 재사용 응답에도 원문 연결과 수치 방어 검사를 다시 적용한다. `llm_call_count`는 캐시를 포함한 논리 요청 수이지 청구 API 요청 수가 아니다.
자연어 MD 비교 예제는 `tests/fixtures/semantic_proof/2`, `4`이며 운영 규칙에 포함되지 않는다. 단일 자연어 instruction 변경으로 3e6 결과의 판정이 바뀌는지 실제 CLOVA로 검증한다.
`validate_corpus.py --live`는 누락·오탐뿐 아니라 보류 또는 개별 시험 오류 누락이 있으면 성공 종료하지 않는다. 과거 결과 파일은 `.local_validation/live/history`에 남는다.
더미 정답표 D03의 in vivo는 정상 PDF/허가서/실제 누락과 모순된다. 제공 문서에서 빠진 시험은 in vitro이므로 그 근거로 검증한다.
D00의 원본19쪽에는 무균시험 결과란에 기준 문장이 반복되어 있어 실제 결과 확인을 보류한다. 정상 파일명만으로 이 문제를 합격 처리하지 않는다.

자동 판정은 검토 보조이며, 새 제품/새 양식/개정 허가서에 대해 검증 없이 무오류를 보장하지 않는다.

`required_tests`는 선택한 범위의 실제 `test` 레코드에서 시험명 또는 상위 시험명을 각각 검색한다.
서로 다른 시험명의 조각을 붙여 필수시험이 있다고 인정하지 않으며 제목(`heading`)만 있는 것은 시험 수행 근거가 아니다.
현재 이 연산의 필수 목록은 MD의 `params.tests`에서 온다. 허가서의 모든 단계/배치별 필수 목록을 자동으로 생성·검사한다는 뜻은 아니다.

## 허가서 전체 목록과 배치별 존재 검사 (v71 선택 적용)

`permit_required_tests`는 고정된 `tests` 배열 대신 허가서의 정확한 전체 제목 경로 아래 말단시험을 모두 읽는다.
Python의 제품별 시험명 코드를 고치지 않고 MD의 제품·단계·명칭 대응·배치 필드/연결·원문 범위를 정한다.
예제는 `docs/examples/required_test_rules/rules.md`이고 운영27규칙과 분리되어 있다.

이 첫 버전은 담당자가 **그 하위 문단들이 모두 무조건 필수임을 검토한 범위**만 받는다.
허가 내용·시험·계층의 해시(`reviewed_scope_sha256`)와 문서 전체 파일 해시(`reviewed_document_sha256`)를 모두 고정한다.
상위 장/서문/이미지 등 전체 허가서의 변경도 보류하며, 메타데이터만 바뀌어도 재검토가 필요할 수 있다. 해시는 승인 서명이 아니다.
조건부 수행, 용기별 의무, 시험 차수의 자동 LLM 해석은 아직 연결하지 않았다. 해시만 자동 복사해 보류를 지우지 않는다.

원문 목록을 읽기 전용으로 확인하는 예:

```powershell
.\.venv\Scripts\python.exe scripts/inspect_permit_requirements.py --permit '더미데이터/260922[더미허가문서]스카이코비원멀티주.pdf' --stage-title '제조방법 및 시험기준' --stage-title 'Component A 중간체 원액' --stage-title 'Component A 본배양액에 대한 시험'
.\.venv\Scripts\python.exe scripts/validate_rules.py --rules-dir docs/examples/required_test_rules
.\.venv\Scripts\python.exe scripts/prove_required_test_policies.py
.\.venv\Scripts\python.exe -m pytest tests/test_permit_required_tests.py tests/test_required_test_policy_pdf.py -q
```

첫 명령은 본배양액의4시험/물리11쪽/문서지문/문단ID를 보여줄 뿐 규칙을 승인하거나 MD를 변경하지 않는다.
합성 검증은 정상·시험누락·범위누락·2배치정상·2배치중1시험누락·배치미정·허가조건변경7사례다.
새 PDF는 `.local_validation/required_test_proof/`에 만들고 원본 더미는 보존한다. 이 proof는 CLOVA를 호출하지 않는다.

배치 목록은 시험 레코드에서 역산하지 않고 별도 content/info에서 확인한다. 복수 배치는 각 시험의 명시적 제조번호가 필요하다.
시험명 조각을 붙이거나 상위 묶음 하나로 모든 하위 시험을 채우지 않는다. 검색 별칭은 명칭 동등성으로 인정하지 않는다.
누락 FAIL은 원문 검사 범위와 배치 연결이 확인된 경우만 가능하며, 원문 언급은 있으나 추출이 빠졌거나 OCR/중복/연결이 불명확하면 HOLD다.
이미 확인된 누락과 다른 불완전 근거가 함께 있으면 FAIL을 유지하고 감사 정보에 보류 항목도 남긴다.

이 연산의 PASS는 필수 **시험 결과 기록이 존재**한다는 뜻이다. 결과의 수치/정성 적합은 기존 개별 판정이 따로 검사한다.
새 양식·표형 배치·스캔본의 추출을 보증하지 않으며, 실제 제품에서 원문 연결을 검증한 뒤 운영 MD에 추가해야 한다.

v75는 `test_coverage_start/end`로 정보 절과 시험 절을 독립 지정하는 선택형 계약도 지원한다.
중간의 다른 제조단계 언급은 대상 시험의 수행 근거로 빌리지 않는다. 시험 구간 안의 미추출 언급·중복·
결과 누락은 보류하며, 정확한 경계/모든 선택 레코드의 원문 연결이 확인된 범위에서만 누락을 판정한다.
`docs/BATCH_FIELD_LINKING.md`에 설정 조건과 한계를, `docs/examples/test_scope_rules/rules.md`에
운영 규칙과 분리된 전체 예제를 기록했다. 이는 조건부 의무 LLM 자동 해석이나 전체 허가 검토를 대신하지 않는다.
