## 사용자 목적과 성공 기준

회사 현장에서 처음 받는 긴 SP와 허가서를 사람이 PDF 파일로 잘라 올리지 않아도 검수한다.
허가서 권위, 제품·제조단계·시험대상·배치 구분, 모든 적합 조건의 확인을 유지하면서
불필요한 검색 후보와 동일 근거의 반복 전송을 줄인다.

목표 입력 규모는 SP 200~300쪽 이상, 허가서 300쪽 이상이다. 이 규모를 처리했다고
주장하려면 실제 해당 규모의 검증을 별도로 완료해야 한다. 작은 D00/D07의 통과나
동일 페이지 반복 확대 자료만으로 새로운 회사 문서의 정확도·속도를 보증하지 않는다.

최종 판단의 의미는 LLM이 담당하고, 코드는 원문 연결·조건 누락·응답 ID·전송 예산을 검증한다.
확인되지 않은 숫자 파싱으로 LLM의 판정을 대체하지 않는다. 추출/OCR 오류, 서비스 장애,
문서 근거 부족은 구분한다.

## 현재 코드에서 확인한 사실

- `permit_pdf_store.py`는 페이지를 넘는 section chunk, 제조단계/시험명,
  `owned_spans`, `parent_evidence_id`를 이미 가진다.
- `permit_index.py`는 PDF 내용/추출 설정에 따른 지속 인덱스와 단계·시험 검색 키를 가진다.
- `PermitPdfStore.search()`는 현재 chunk를 순회하여 점수를 매긴다.
  구체적인 단계와 시험명이 맞으면 다른 단계의 후보를 제외하는 기존 보호 장치가 있다.
- `judgement.py::_get_permit_context()`는 최대 12개 후보를 요청한다.
  authoritative 경로는 후보 원문을 문자수로 절단하지 않는다.
- `llm.py::explain()`은 일반 업로드에서 `GroundedPermitResponse` 및
  `candidate_id`/`clause_id`를 사용한다. `grounded_verdict()`가 실제 원문을 연결한다.
- 일반 업로드의 `pipeline.py`는 시험 레코드별 판정을 실행한다. 같은 허가기준이
  여러 레코드의 요청에 반복될 수 있다.
- 현재 `GroundedGroupBatchResponse`는 deterministic-first 조건/fact 모델용이다.
  일반 업로드를 이 경로에 강제로 연결하면 D07의 14일+14일/28일, 불용성이물 의미 해석
  회귀를 되살릴 수 있으므로 그대로 사용하지 않는다.
- 로컬 D07 43.26초, D00 43.58초 기록은 각각 `cache_only=true`, 캐시 적중 105건,
  HTTP 0건이었다. 이 수치는 신규 문서의 최초 처리 성능 기준에서 제외한다.

## 접근법 비교와 선택

1. **검색만 개선:** 변경 범위는 작지만 시험별 호출 수는 거의 그대로 남는다.
2. **검색 + 원문 보존 + 의미 판정 근거 공유 묶음:** 선택안.
   검색량과 중복 입력을 줄이고, 결과는 레코드별로 독립 검증한다.
3. **일반 업로드를 기존 deterministic-first로 전환:** 제외.
   전송 최적화와 판정 의미 변경을 혼합하며 이미 확인된 회귀 위험이 있다.

새 벡터 DB, 별도 임베딩 API, 외부 문서 업로드 서비스는 이번 범위에 추가하지 않는다.
먼저 기존 구조화 키와 로컬 텍스트 검색을 활용한다. 근거 없는 동의어 추정은 하지 않는다.

## 1. 검색 후보를 정밀하게 줄이기

### 검색 단계

1. 현재 제출에 연결된 허가서와 기존 제품 정책으로 검색 범위를 제한한다.
2. 정규화한 제조단계·시험대상·시험명과 명시적으로 승인된 별칭으로 찾는다.
3. 정확한 후보를 확정하지 못하면 기존 어휘 점수 검색으로 범위를 넓힌다.
4. 여러 허가서/동일 단계의 상충 후보는 유지한다. 점수가 높다는 이유만으로 하나를 정답으로
   선택하지 않는다. 최종 의미 매칭은 LLM이 수행한다.

인덱스 로드 시 단계/시험별 lookup과 chunk별 토큰을 미리 준비한다.
동일한 검색 질의를 한 검수 안에서 다시 계산하지 않도록 재사용할 수 있지만,
질의에 실제로 사용되는 필드를 모두 키에 포함한다. 다른 시험결과를 가진 질의가
임의로 같은 검색 결과를 공유한다고 가정하지 않는다.

기존 정책이 없거나 구조를 확정할 수 없는 경우 기존 검색으로 되돌아간다.
`top_k`를 12에서 1~2로 일괄 축소하는 방식은 사용하지 않는다.
정확한 동일 단계/시험의 후보가 전송 예산을 넘으면 일부를 조용히 버리지 않는다.

## 2. 검색 단위와 판정 근거 단위 분리

검색은 작은 section으로 하되 판정에는 **완결된 시험 근거 묶음**을 사용한다.
부모 시험의 공통 조건, 선택된 하위시험 조건, 페이지를 넘는 본문/표/각주를 원문으로 연결한다.

- 부모 제목만 같다는 이유로 모든 형제 시험을 합치지 않는다.
- 번호는 원문 위치 및 명시적 교차참조를 연결하는 데만 사용하고, SP와 허가서 시험의
  의미적 동일성을 결정하는 키로 사용하지 않는다.
- 참조 대상이 유일하게 해석되지 않으면 근거가 완결되었다고 표시하지 않는다.
- parent graph의 순환, 다른 문서로의 잘못된 연결, 끊어진 참조를 검사한다.
- 하나의 원문 span을 두 번 실어도 두 개의 독립 조건으로 잘못 취급하지 않도록 span ID를 유지한다.
- 원문 인용은 LLM이 다시 쓰는 것이 아니라 로컬 원문 span에서 가져온다.

예: 유정란접종시험의 요막강/난황낭, 난령, 최소 개수, 온도, 1차 및 계대 배양기간,
각 단계 생존율, 혈구응집 조건을 해당 시험의 관계와 함께 보존한다.
21일 조건과 다른 시험의 28일 조건, 중간 배양기간과 전체 관찰기간을 섞지 않는다.

이 연결이 불확실한 시험은 일반 단건 원문 판정으로 유지한다.
내용을 잘라서 모델 입력 한도에 맞추거나, 검색 실패를 조건 없음으로 바꾸지 않는다.

## 3. 일반 업로드용 근거 공유 의미 판정

### 기존 경로와 분리

기존 `GroundedPermitResponse`의 의미와 검증을 유지하는 별도 묶음 envelope를 만든다.
`GroundedGroupResponse`의 숫자/기간 조건 파싱을 일반 업로드의 판정 권한으로 사용하지 않는다.
기존 catalog/제품 보정 deterministic-first 정책, 다른 회사·제품 매핑, 버전 로직은 그대로 둔다.

### 전송 구조

- `evidence_sets`: 원문 및 절차/적합 조건을 담은 공유 근거 집합.
- `records`: 고유 `record_id`, 해당 `evidence_set_id`, 현재 SP 레코드의 기준/결과/방법/
  기간/대조군/표/배치 문맥.
- `responses`: 레코드별 의미 매칭, 선택 후보, 모든 clause의 판정과 이유.

각 `record_id`는 한 실행 안에서 유일하며 원래 레코드 위치로 되돌릴 수 있어야 한다.
후보/clause ID는 소속 근거 집합과 함께 검증한다. 모델이 반환한 순서로 원래 행에 배분하지 않는다.

공유 가능한 것은 **동일한 허가기준 원문과 관계**뿐이다. 같은 시험명이더라도 허가서,
제품, 제조단계, 대상, 시험방법, 조건 또는 문맥이 다르면 근거 집합을 공유하지 않는다.
서로 다른 배치의 SP 결과를 합치거나 판정을 복제하지 않는다. 배치 문맥이 모호하면 묶지 않는다.

단계적 도입을 위해 첫 버전에서는 SP 레코드의 의미적 중복 판정 재사용을 추가하지 않는다.
동일 기준에 대해 결과가 다른 여러 행을 독립 판정하면서 공통 원문의 중복만 줄인다.
기존 완전 동일 요청 캐시는 별도로 유지한다.

### 크기와 응답 예산

- 초기 묶음 상한은 4개 독립 레코드다. 상한까지 채우기보다 근거 공유가 가능한 행을 우선한다.
- 기존 60,000자 제한은 보조 안전 제한으로만 사용한다. 문자수를 토큰수라고 표시하지 않는다.
- 후보 수, 전체 입력 크기, 조건별 응답 수와 모델의 입출력 예산을 함께 검사한다.
  예산이 확인되지 않거나 공유 이득이 없는 요청은 기존 단건 경로로 보낸다.
- 단건 자체가 모델 예산을 초과하면 절단하지 않고 대조 미완료의 원인으로 명시한다.
- 무제한 병렬 호출, 기존 요청 간격/429 보호 장치 해제, 대용량 실패의 무한 재시도는 금지한다.

### 결과와 실패 처리

- 레코드/근거/후보/clause ID 및 모든 필수 조건의 정확한 포함 여부를 검증한다.
- 누락·중복·잘못된 ID 때문에 다른 행의 결과를 적용하지 않는다.
- 명확하게 특정 가능한 잘못된 항목은 그 항목만 기존 단건 검증으로 제한적으로 보정한다.
- 요청에 없던 record ID 등 묶음 경계를 신뢰할 수 없는 응답은 전체 envelope를 거부한다.
- 보정은 실행당 각 항목 최대 1회이며, 최초 묶음과 보정을 모두 실제 호출 수로 기록한다.
- 보정 후에도 원문 연결이 검증되지 않으면 기존과 같은 근거 불충분 처리를 한다.
- 단, 잘못된 JSON/schema, 식별 불가능한 응답 항목 등 프로토콜 실패는 문서의 근거 부족과
  다르다. 허용된 형식 보정 후에도 실패하면 서비스 응답 오류로 중단하고 HOLD로 표시하지 않는다.
- 정상 FAIL/HOLD를 PASS로 만들기 위해 재호출하지 않는다.
- 401/403/429/timeout/연결 실패는 서비스 오류로 전파하고 최종 결과 게시를 중단한다.
  서비스 오류를 문서 PASS/FAIL/HOLD로 바꾸지 않는다.

SP 기준의 비교용 결과와 기존 문서 공통 규칙은 유지한다. 새로운 전송 경로에서 근거가 없다는
이유로 SP 기준 fallback을 새로 확대하지 않는다. 실제 누락/모호함의 처리는 기존 정책에 따른다.

## 4. 적용과 캐시 경계

개발 중 새 경로는 명시적인 실험 모드로만 켠다. 기본 기존 모드와 대조할 수 있어야 한다.
일반 업로드의 기본값 전환은 아래 정확성·최초 처리 검증을 통과한 뒤 결정한다.
실험 모드는 키/문서를 다른 서비스로 보내거나 다른 제품의 정책을 바꾸는 권한이 아니다.

공유 근거/묶음 프로토콜 버전, 검색 설정, 원문 내용, 추출 스키마, 적용 정책, 실행 모드는
응답 및 완료 결과 캐시의 의미적 식별에 반영한다. 새 경로에서 이전 전체 판정 결과를
그대로 돌려주어 속도가 빨라진 것처럼 측정하지 않는다.

기존 읽기/OCR 인덱스는 입력과 추출 의미가 같으면 활용한다. 캐시 검증에는 PDF 내용과
버전/설정을 사용하며 파일명만으로 다른 문서를 같은 것으로 판단하지 않는다.
키 원문은 어떤 fingerprint, 로그, 테스트 산출물에도 기록하지 않는다.
캐시나 사내 원문을 GitHub로 옮기는 작업은 포함하지 않는다.

## 5. 진단과 성능 측정

최소 측정 항목:

- SP 추출, 허가서 추출/OCR, 인덱스 로드/생성, 검색, 요청 준비, LLM 총 경과시간.
- SP 시험행 수, 검색 후보 수, 근거 공유 전/후 입력 문자수, 묶음 수와 각 묶음 크기.
- 실제 HTTP 시도, 재시도, 보정, 응답 캐시 적중, 완료 결과 캐시 적중.
- 응답 대기/호출 간격 대기는 가능할 때 별도로 측정하며 합계에 중복 계상하지 않는다.
- provider가 반환한 실제 token usage가 있으면 기록하고, 추정치와 구분한다.
- 원문·프롬프트·키를 진단 로그에 덤프하지 않는다.

성능 비교는 세 조건으로 나눈다:

1. 허가 인덱스/LLM 응답/완료 결과가 모두 없는 최초 실행.
2. 허가 인덱스만 재사용하고 SP 및 LLM 응답/완료 결과는 새로 처리하는 실행.
3. 기존 LLM 응답 재사용 실행(참고치; 최초 처리 개선의 증거로 사용하지 않음).

비교에는 동일 모델/입출력 설정/문서/규칙 버전을 사용한다. 캐시 삭제 대신 격리된 실험
디렉터리를 사용해 사용자의 기존 캐시와 결과를 보존한다. 외부 장애/429가 발생한 시간은
숨기지 않고 별도 표기한다. 계정 한도나 최초 처리시간 몇 초를 보장하지 않는다.

## 6. 검증 기준

### 검색 및 근거 완전성

- 같은 시험명이라도 다른 제조단계·제품·문서의 기준이 섞이지 않는다.
- 시험명이 다르거나 구조가 불확실하면 무리한 축소 없이 기존 후보 검색으로 돌아간다.
- 같은 단계/시험의 상충 허가기준, 12개를 넘는 필요한 후보, 다중 문서를 검사한다.
- 부모 공통 조건, 자식 시험, 페이지를 넘는 표/각주, 유일/모호한 참조, graph 순환을 검사한다.
- 유정란 복합 조건 각각의 위반/누락을 독립 변형한 fixture로 조건 누락을 잡는다.

### 묶음 응답

- 서로 다른 배치에 PASS/FAIL/HOLD가 섞인 요청의 결과가 행별로 정확히 연결된다.
- 서로 다른 원본 위치/표 하위행에 같은 `order_idx`가 있어도 결과 연결은 충돌하지 않는다.
- missing/duplicate/extra ID, 타 근거 clause, 누락 조건, 잘못된 타입, 응답 순서 변경,
  일부 손상과 전체 프레이밍 손상, bounded repair, 서비스 오류 전파를 검사한다.
- 같은 기준을 8개 레코드가 공유하고 크기 제한을 만족하는 fixture는 최초 provider 요청이
  최대 2개이며, 후보 원문이 요청 내 레코드 수만큼 반복되지 않는다. 보정 호출은 따로 센다.
- 허가기준이 서로 다른 경우 공유하거나 입력 일부를 삭제하지 않는다.
- 정수/범위/부정 표현/단위/소수 자릿수/기간 조건이 이전과 다른 판정 의미로 바뀌지 않는다.

### 회귀 및 실제 성능

- `test_direct_upload_semantic_regression.py`의 14일+14일/28일 및 불용성이물 사례를 유지한다.
- 기존 제품 매핑, 버전 경고/표시, 저장기간, 서명일, 제조량, 필수 항목 검사 결과를 비교한다.
- D00/D07의 레코드별 판정·근거·이유를 확인한다. 총 PASS 개수만 같다고 통과시키지 않는다.
- 단위 테스트의 provider 대역은 입력/출력 계약 검증용이다. 실제 LLM 정확성 증명과 구분한다.
- 전체 pytest와 권한 있는 실제 provider smoke/콜드 비교를 구분해 보고한다.
  실제 provider 비교가 미실행이면 기본 모드를 전환하지 않고 남은 검증을 명시한다.
- 기존 300쪽 이상 자료가 있으면 조건 1/2로 측정한다. 없으면 실제 규모 검증 미완료로 기록한다.
