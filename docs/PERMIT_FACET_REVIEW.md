# 허가 원문의 의미를 독립적으로 묻는 검토 초안

기존 분류 초안에서 한 문장의 `적합 기준 + 절차 + 약전 참조` 중 대표 범주 하나만 고르는 문제가 발견됐다.
`scripts/permit_facet_review.py`는 한 요청에서 한 의미만 질문하고, 같은 원문에 대해 각각 독립 응답을 받는다.
질문 설명은 `docs/examples/permit_semantic_facets.md`의 각 `## 분류_id` 본문에 있다.
MD의 설명만 변경하면 새로운 질문/계획 지문으로 검토할 수 있다.

이 기능은 실제 SP 판정 경로에 연결하지 않은 **미승인 검토 도구**다. 새 UI나 운영 규칙은 아니다.
어느 경우에도 시험 필수/면제/합격 또는 검토 승인 상태를 생성하지 않는다.

## 원문과 모델의 역할

- 코드가 기존 전체 허가 원문 목록을 가져오고, 각 구간의 모든 문자를 줄 단위로 분할한다. 검색 상위 결과만 사용하는 방식이 아니다.
- 원문 줄은 문자 하나도 재작성하지 않으며 문단/구간 ID, 물리 쪽, 정규화 페이지 문자 위치에 연결된다.
- 모델은 해당 의미가 `present`/`absent`/`unclear`인지 답하고, 같은 원문 구간 안의 줄 ID만 선택한다.
- 모델에게 원문 인용을 다시 쓰게 하지 않는다. 코드가 선택한 줄의 원문을 복원한다. 모델 설명은 별도 필드다.
- `present`는 비어 있지 않은 원문 근거가 필요하고, `absent`는 근거 목록이 비어 있어야 한다. `unclear`는 미확정 상태 그대로 보존한다.

이 방식도 모델의 의미 판단이나 선택한 줄의 의미 적합성을 자동 보증하지 않는다.
ID·인용 일치 검사가 통과해도 엉뚱한 내용의 줄을 선택할 수 있다. 별도 의미/근거 검토가 필요하다.
`absent` 역시 모델의 부재 제안일 뿐이며 시험 면제 또는 자료 전체에 조건이 없다는 증명이 아니다.

## 안전장치와 재현

`build_review`는 원문/MD 실제 바이트/설정/코드/전체 요청과 범위를 고정한다.
매 요청 전후 다시 검증하고, 실행 중 원문·MD가 바뀌면 기존 응답을 수락하지 않는다.
원문 전체를 줄로 나누므로 빈 줄과 머리말도 문서 목록에서 제거하지 않는다. 빈 줄을 판정 근거로 선택하는 것은 거부한다.
누락·중복·잘못된 구간/근거/응답 개수·임의 승인 필드는 거부하며 실패 시 뒤 요청을 호출하지 않는다.

일부 구간이나 일부 의미만 지정한 실험은 `partial_scope: true`다. `contract_complete`는 지정한 요청 조합의
응답 계약만 완비됐다는 뜻이다. 전체 의미 검토 완료가 아니며 `semantic_correctness_verified: false`,
`runtime_activation: false`, `unreviewed`를 유지한다.

API 형식 오류가 나면 모델 본문을 보존하지만 키/요청 헤더/HTTP객체/제공자 오류 상세는 남기지 않는다.
캐시에서 받은 응답은 제공자 호출 관찰로 세지 않는다. 네트워크 재시도/청구 금액과 논리 요청 수는 구별해야 한다.
파일 저장/재개는 별도 `permit_facet_checkpoint.py`가 담당한다. UI 승인 기능은 없다.
기존 CLOVA 클라이언트의 HTTP429 대기는 유지하되 분류 오류에 대한 자동 재요청은 하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_permit_facet_review.py -q
```

실제 더미 검증의 고정 원문·표본·성공/실패 결과는 `WORK_STATUS.md`에 기록한다.
이 표본에서 성공하더라도 전체276구간/나머지 의미/다른 문서의 검토 완료는 아니다.
실제 허가 의무와 기존 검토형 MD로 연결하기 전 별도의 회귀와 승인 범위 확인이 필요하다.

## v87 제한 실험 결과

15구간에 네 가지 의미를 각각 질문해60응답을 받았다. 사전에 정한42개 상태 기대값을 비교하면
최초에는12/15구간이 일치했고, 긍정 근거22개 중21개만 해당 의미의 핵심 구절을 포함했다.
제목/변경이력을 실제 수행 설명으로 읽고, 수치 조건의 중간 줄을 근거에서 빠뜨리는 문제가 있었다.

Python 코드와 원문은 그대로 두고 MD만 보완한 뒤, 같은15구간의42기대값 및22근거 검사를 모두 통과했다.
이는 사용자가 원한 **MD 설명 변경으로 LLM 검토 방식이 바뀌는 경로**의 제한된 실제 증거다.
표본에 맞춰 보완한 후 재검증한 결과이며, 독립 미사용 표본의 일반화/전체60상태 정답/전체문서 무오류를 증명하지 않는다.
실험 원본 실패는 보존했고, 운영 UI·판정 엔진·기존 MD 규칙은 변경하지 않았다.
전체 자동시험은 신규41개를 포함한1282개 통과(skip0)다. 이 개수와 LLM 의미 정확도를 혼동하지 않는다.

각 실험의 정답 개수가 다른 것은 일부 의미/구간을 선택했기 때문이며, 독립 holdout이나 전체7의미 완료가 아니다.

MD 비교본은 `.local_validation/permit_facets_v90/candidate-facets.md`에만 보존했다.
기존 `docs/examples/permit_semantic_facets.md`와 운영 MD에 반영하지 않았다.
유료 실험은16논리요청/제공자 응답 관찰16, 전체245요청은 계획만 생성/API0이다.
자동 감사 `.local_validation/audit_v90.py`는 실제 전송 내용의 차이, 원문 복원, 실패 근거 보존,
기존 UI/엔진·원본15파일·D00~D12 저장26결과 불변까지 대조한다. 새 SP 판정/브라우저 검수는 아니다.

다음 설계에서는 기존 packet의 `page_label_audit`에 있는 **페이지 번호 후보의 원문 위치**를
검토용 정보로 활용할 수 있는지 확인한다. 후보는 확정된 페이지 번호가 아니므로 측정 비율과의
반례 및 원문 좌표 대조가 필요하다. 본문을 삭제하거나 후보를 자동 정답으로 취급하지 않는다.
모델의 자체 설명·형식 성공만으로 검토 승인이나 운영 활성화를 하지 않는다.

## v91 위치 단서 대조와 자료형 검증

`--layout-hints --evidence-units clauses`는 원문 내 분수형 후보의 물리 쪽·문자 위치·소유 ID와
정확한 인용을 검증한 뒤 `possible_page_label`/`unreviewed` 정보를 추가하는 **실험용 옵션**이다.
기본값은 off이고 운영에 연결하지 않았다. 측정 비율일 수도 있으므로 페이지 번호로 확정하거나
본문에서 지우지 않는다. 전체 원문276구간·22,217문자·989단위와 표시654단위는 그대로이며,
기존 후보22개를 위치 단서22개로 연결했다. 기본off의 lines/clauses 질문은 v90과 동일하다.

원래 MD와 정답을 고정하고 한 구간씩 비교한 결과, 위치 단서는 의미 판단을 개선하지 못했다.

| 비교 범위 | 상태 정답 | 긍정 근거 | 남은 오류 |
|---|---|---|---|
| 기존4구간×2의미 | 6/8 | 3/4 | 완결 본문 오탐2개, 페이지를 절단 근거로 선택 |
| 새 수동 정답 실제4구간×2의미 | 7/8 | 3/4 | 완결 본문 오탐1개, 절단 근거 대신 페이지 선택 |
| 같은3/4의 측정 비율/페이지 표기 합성4사례 | 5/8 | 3/3 | 측정 비율2개를 안내로 오인, 정상 페이지 사례 불완전 오탐 |

모든24요청은 출력 계약을 통과했지만 의미 정확성과는 다르다. 긍정 근거3/3은 부정 사례의
오탐을 포함하지 않으므로 전체 성공이 아니다. 기존4구간은 v90의 상태8/8보다 나빠졌다.
새 실제 구간은 기존 수동 보완 표본과 분리했으나 같은 PDF는 과거 전체 초안 추출에 사용됐다.
새 독립 문서 시험이나 전체7의미 평가로 해석하지 않는다. 새 골드는 API 호출 전에
`tests/fixtures/permit_layout_probe_v91.json`에 고정했고, PDF 물리4/9/10/11쪽을 렌더 대조했다.

따라서 **실험 옵션을 기본off로 유지하고 운영에 적용하지 않는다.** 모델의 잘못된 근거를
정답 ID로 자동 교정하지 않는다. 원래 MD와 v90의 별도 실패 비교 MD도 변경하지 않았다.
실험은24논리요청/제공자 응답 관찰24이며429 backoff가 있어 청구 건수와 같다고 단정하지 않는다.
전체245요청은 계획만 생성/API0이다. 좁은 실패가 남아 전체 유료 실행을 확대하지 않았다.

별도 API0 검증 중 Python의 `True == 1 == 1.0` 때문에 계획을 단순 비교하면 자료형 변경을
놓치는 문제를 발견했다. 후보의 정수 자료형을 엄격히 검사하고, 계획은 정규 직렬화 지문으로
비교하도록 고쳤다. 추가8개 실패를 먼저 재현한 뒤 관련130개, 최종 전체 **1,378개 통과/skip0**를
확인했다. 이번 신규29개 검사는 이 방어와 원문 위치 대응/옵션/재개를 다루며 의미 정답 보증은 아니다.

실험 당시 소스와 SHA는 `permit_facets_v91/pre-guard-source.json`에 보존했다. 최종 guard 변경이
실제 질문/요청을 바꾸지 않았음을 대조했고, 구현 지문이 다른 옛 계획은 자동 재개되지 않는다.
별도 폴더에서 저장된 실제 응답8개를 새 계획으로 API0 재검증한 뒤 재개했을 때8개 모두
재사용되고 원래 결과와 실패 근거까지 동일했다. 이는 Streamlit 미완료 작업 복구 기능이 아니다.
감사는 `.local_validation/audit_v91.py`/`v91-audit.json`을 따른다. 원본15파일·저장SP26결과·
운영 엔진/UI는 불변이며 새 SP 전체 판정이나 브라우저 검수는 수행하지 않았다.

다음에는 분수 모양만의 단서를 늘리지 않고 실제 페이지 배치/본문 연결 또는 독립 근거 적합성
검사를 부정 반례와 함께 좁게 검증해야 한다. 동일 표본 반복 성공을 전체 완료로 간주하지 않는다.

## 계획 저장과 중단 후 재개

별도 CLI `scripts/review_permit_facets.py`는 기본적으로 계획만 만들며 API를 호출하지 않는다.
`--live`가 유료 호출을 허용한다. 운영 SP 판정이나 UI에는 연결하지 않았다.

```powershell
.\.venv\Scripts\python.exe scripts/review_permit_facets.py `
  --permit '더미데이터\260922[더미허가문서]스카이코비원멀티주.pdf' `
  --stage-title '제조방법 및 시험기준' `
  --stage-title 'Component A 중간체 원액' `
  --stage-title 'Component A 중간체 원액에 대한 시험' `
  --output-dir '.local_validation/my-permit-review'
```

위와 같은 인수에 `--live --resume`을 붙이면 저장한 계획을 실행한다. 전체276구간×7의미는245묶음 요청이므로,
현재 의미 검증 한계가 남은 상태에서 기본 전체 범위를 반복 호출하지 않는다.
`--span-ref S0001` 또는 `--facet external_reference`를 반복 지정하면 명시적 부분범위로 계획을 만들 수 있다.

- 원문/MD/설정/구현/요청 지문이 같은 경우에만 재개한다. MD를 고쳤다면 **새 출력 폴더**가 필요하다.
- 요청 직전에 시작 기록, 응답 계약 검증 뒤에 완료 기록을 각각 생성한다. 기존 기록은 덮어쓰지 않는다.
- 검증된 응답은 원문을 다시 대조하고 재사용한다. 재사용 자체로 의미를 승인하지 않는다.
- 실패 응답 또는 시작만 있고 완료 기록이 없는 요청은 자동 재호출하지 않는다.
- 확인 후 같은 명령에 `--live --resume --retry-failed`를 명시해야 실패/중단 요청을 새 시도로 기록한다.
  중단 직전에 제공자가 이미 응답했을 수도 있으므로 **비용이 다시 발생할 수 있다**.
- 손상/누락/다른 지문의 파일은 `--retry-failed`로도 우회하지 않는다. 자료를 보존해 별도 진단한다.
  과거 실행에서 수락했던 요청의 시작/완료 파일이 사라졌다면 빈 요청 폴더가 남아 있어도 미실행으로 취급하지 않는다.
- 같은 출력 폴더에는 운영체제 파일 잠금으로 한 프로세스만 들어간다. 프로세스가 끝나면 잠금은 해제된다.
  `.lock` 파일이 남아 있다는 사실만으로 실행 중인 것은 아니다. 다른 출력 폴더의 중복 호출까지 막는 전역 잠금은 아니다.
- 중단 중 쓰다 만 JSON은 복구한 것처럼 추정하지 않고 손상으로 거부한다. 파일마다 flush/fsync하지만 정전·디스크 고장에 대한 영구 보관 보장은 아니다.
- `requests/FxxBxxx/`의 시작/완료 기록과 `runs/run000001.json` 등 실행 결과를 보존한다.
  모델 본문만 감사하며 API 키/HTTP 헤더/제공자 예외 본문은 저장하지 않는다.

이 재개 기능은 독립 허가 검토 CLI에 한정된다. Streamlit 서버 재시작 후 미완료 SP 작업 자동 복구 기능과는 다르다.
체크포인트 구현 파일 자체가 바뀌어도 이전 작업의 자동 재개는 거부한다. 개발 과정에서 저장한 응답을 새 구현으로
검사하는 API0 재생 시험은 별도 폴더와 원응답 지문으로 기록하며, 새로운 CLOVA 호출로 집계하지 않는다.
