# 회사·제품·전체 디테일 작성 가이드

## 1. 목적

제약 도메인 담당자가 회사 방문과 제품 회의에서 확인한 검수 관점을 Markdown으로 관리하고, LLM이 문서를 판정할 때 공통 관점과 해당 회사·제품의 관점을 모두 확인하도록 하기 위한 가이드다.

디테일 문서는 판정 결과를 미리 적는 파일이 아니다. 어떤 항목을 확인해야 하는지, 같은 의미의 단계와 필드를 어떻게 연결해야 하는지, 어떤 혼동을 피해야 하는지를 기록한다.

MD 문장만으로 새 추출기나 검증 코드가 자동 생성되지는 않는다. 규칙 변경 후 PDF별 정답지와
실행 이력을 확인하는 방법은 `docs/RULE_REGRESSION_AND_RAG_OPERATIONS.md`를 참고한다.

## 2. 세 계층의 책임

### 전체 디테일

경로: `sp_pdf_judger/domain_details/overall.md`

모든 회사와 제품에 반드시 적용되는 원칙을 쓴다.

- 시험기준과 시험결과의 의미 비교
- 단위와 범위
- 공정 선후관계와 병렬 공정 합류
- 제조번호·제조일·제조량 정합성
- 제조량과 사용량 구분
- OCR 및 표 추적성
- 근거 우선순위와 보류 원칙

### 회사 디테일

경로: `sp_pdf_judger/domain_details/companies/<회사>.md`

회사 문서 전반에 반복되는 용어와 관행을 쓴다.

- 회사 표준 제조단계 명칭과 약어
- 제조번호 형식과 단계 전환 규칙
- 제조소·위탁기관·시험기관 관계
- 회사가 중요하게 관리하는 품질속성
- 회사 문서에서 자주 나타나는 표 구조와 예외

제품 하나에만 해당하는 기준은 회사 파일에 쓰지 않는다.

### 제품 디테일

경로: `sp_pdf_judger/domain_details/products/<제품>.md`

같은 제품군에 반복되는 흐름과 핵심 검수 항목을 쓴다.

- 제품의 제조 흐름
- 분기 및 합류 구조
- 단계별 중요 시험
- 용기 규격 또는 농도 선택 규칙
- 제품 특유의 원료·중간체 추적 관계

회사 고유 규칙은 제품 파일에 쓰지 않는다.

## 3. 적용 예시

입력 문서:

```text
회사: GC녹십자
제품: 녹십자-알부민주20%
```

LLM이 함께 확인하는 파일:

```text
overall.md
companies/gc_biopharma.md
products/albumin.md
```

따라서 `시험기준과 결과가 맞아야 한다`는 공통 원칙, `GC녹십자`의 혈장 추적 관점, `알부민`의 원료혈장→원획분→원액→완제 흐름이 한 요청에 모두 들어간다.

## 4. 파일 템플릿

```markdown
---
scope: company
id: gc_biopharma
title: GC녹십자
aliases:
  - GC녹십자
  - 녹십자
  - GC Biopharma
status: active
review_status: draft
priority: 20
owner: 홍길동
last_reviewed: 2026-07-29
---

# 중점 확인

- 현재 문서에서 반드시 확인할 관계를 쓴다.

# 정상 흐름

- 단계 A → 단계 B → 단계 C

# 예외

- 승인된 예외가 있다면 근거 문서명과 함께 쓴다.

# 회의에서 확정할 내용

- 아직 확인되지 않은 질문을 쓴다.
```

필드 설명:

| 필드 | 설명 |
|---|---|
| `scope` | `overall`, `company`, `product` 중 하나 |
| `id` | 영문 소문자 중심의 고유 ID |
| `title` | UI/로그에서 확인할 대표명 |
| `aliases` | PDF 메타데이터에서 나올 수 있는 실제 명칭 |
| `status` | `active` 또는 `disabled` |
| `review_status` | `draft`, `reviewed`, `approved` 등 운영 상태 |
| `priority` | 별칭이 겹칠 때 높은 파일 우선 |
| `owner` | 내용 책임자 |
| `last_reviewed` | 마지막 검토일 |

`status: disabled` 파일은 로더가 읽지 않는다. 회의 전 초안은 `status: active`, `review_status: draft`로 두면 적용 여부와 승인 상태를 구분할 수 있다.

## 5. 회사 방문 전 질문지

### 문서와 용어

- 회사에서 사용하는 SP 문서 종류와 버전 체계는 무엇인가?
- 제조단계의 공식 명칭과 약어는 무엇인가?
- 같은 단계가 제품마다 다른 이름으로 나타나는가?
- 표의 좌우 전치, 병합 셀, 별도 첨부 등 반복되는 형식이 있는가?

### 제조 흐름

- 원료에서 완제까지 정상 제조 흐름은 무엇인가?
- 병렬 분기와 합류는 어디에서 발생하는가?
- 재처리, 재시험, 재포장 등 승인된 예외 흐름이 있는가?
- 제조번호는 단계가 바뀔 때 어떤 규칙으로 바뀌는가?
- 제조일, 분병일, 포장일, 시험일 중 어떤 날짜를 어떤 비교에 사용하는가?

### 시험과 품질

- 절대 누락되면 안 되는 중요 품질속성은 무엇인가?
- 제품 규격, 농도, 용기별로 기준 선택이 달라지는 시험은 무엇인가?
- 외부 시험기관 또는 위탁 제조의 책임 경계는 어디인가?
- 결과 표현의 회사 표준 용어는 무엇인가?

### 근거와 승인

- 회사 기준, 허가서, 약전이 충돌할 때 우선순위는 무엇인가?
- AI가 자동 판정하면 안 되고 사람 확인이 필요한 항목은 무엇인가?
- 디테일 파일의 최종 승인자는 누구인가?

## 6. 좋은 문장과 피해야 할 문장

좋은 예:

```text
- 제조요약도의 제조량은 본문 표의 제조량과 비교하고, 사용량은 비교 대상에서 제외한다.
- Component A와 Component B의 각 분기 순서를 확인한 뒤 나노파티클원액 합류 순서를 확인한다.
```

피해야 할 예:

```text
- 알부민은 항상 합격이다.
- 제조량은 500 L여야 한다.
- 이 회사 문서는 대체로 맞으므로 통과시킨다.
```

고정 수치는 적용 대상, 문서 버전, 출처가 명확하지 않으면 쓰지 않는다. 가능한 경우 기준값은 허가서 또는 SP에서 검색하게 하고, 디테일에는 올바른 기준을 선택하는 규칙을 쓴다.

## 7. 충돌 처리

적용 우선순위:

```text
현재 SP/허가서의 명시적 내용
→ 결정적 코드 규칙
→ RAG 근거
→ 제품 디테일
→ 회사 디테일
→ 전체 디테일
```

제품 디테일은 전체 디테일을 없애지 않고 추가한다. 디테일끼리 충돌하면 더 구체적인 제품 항목을 참고하되, 현재 SP나 허가서의 명시적 근거를 넘어서는 판정을 만들지 않는다.

## 8. 추가 절차

1. 가장 가까운 기존 MD를 복사해 새 파일을 만든다.
2. `scope`, `id`, `title`, `aliases`를 수정한다.
3. 회의에서 확인한 내용과 미확정 질문을 분리한다.
4. 다음 명령으로 매칭을 확인한다.

```powershell
python -m sp_pdf_judger.domain_details `
  --company "문서에 표시된 회사명" `
  --product "문서에 표시된 제품명" `
  --show-context
```

5. 출력의 `matched_company`, `matched_product`, `sources`를 확인한다.
6. 대표 정상 문서와 오류 문서로 회귀 테스트한다.
7. 제약 담당자가 `review_status`와 `last_reviewed`를 갱신한다.

## 9. 수정 반영과 캐시

선택된 전체·회사·제품 MD 본문과 메타데이터의 SHA-256 지문이 판정 캐시 키에 포함된다. 내용이 바뀌면 같은 PDF라도 이전 결과를 재사용하지 않고 다시 판정한다.

다만 실행 중인 Python 모듈 코드 자체를 수정했다면 Streamlit 프로세스를 재시작해야 한다. 단순 MD 내용 수정은 다음 판정 요청에서 새 `DomainDetailStore`가 생성될 때 반영된다.

## 10. 책임 구분

제약 도메인 담당자:

- 검수 항목의 정확성
- 회사·제품 용어와 정상 흐름
- 출처, 버전, 승인 상태

AI 담당자:

- 별칭 매칭과 컨텍스트 조립
- 프롬프트와 캐시 무효화
- 검색 품질 및 회귀 테스트
- 디테일 적용 출처의 추적 가능성

두 담당자는 대표 정상·오류 문서를 함께 선정하고, 디테일 변경이 기존 제품의 판정을 의도치 않게 바꾸지 않는지 공동 검토한다.

대표 문서를 판정하면 `OUTPUT`의 PDF별 회귀 Excel에 새 실행 행이 추가된다. 제약 담당자가
확정한 5행 정답지와 비교해 회사·제품 MD 변경이 다른 규칙 결과를 바꾸지 않았는지 확인한다.
