# 추출 근거의 요청별 보존

## 바뀐 점 (v72)

이전에는 같은 PDF 경로·크기·수정시각이면 같은 임시 폴더를 사용했다. 동시에 두 요청이 실행되면 `05_records.json`을 서로 덮어쓰거나, 성공 결과의 원문 근거를 뒤의 실패 요청이 부분 파일로 바꿀 수 있었다. 화면에 남아 있는 판정과 근거 파일이 달라질 위험이다.

이제 `Pipeline.run`마다 OS 임시 폴더의 `sp_pdf_judger_preview` 아래에 짧은 고유 작업폴더를 원자적으로 만든다. 그 안의 `page1.png`, `extract/`, `manufacturing_summary/`는 다른 요청과 공유하지 않는다. 원본 PDF/허가서는 읽기만 한다.

- `metadata.run_workspace`: 이번 실행의 작업폴더.
- `metadata.extract_dir`: 해당 결과가 실제 사용하는 추출 원문 폴더.
- `metadata.extraction_reused`: 이전 추출 원문을 재사용하는지 여부.

허가서 적용 전/후 두 번 판정할 때는 이전 `extracted_records`와 `static_result`를 함께 넘긴다. 이 경우 원문 폴더/표지/제조요약도는 읽기 전용으로 재사용하며, 빈 새 폴더를 원문 출처로 잘못 기록하지 않는다. `static_result`가 다른 PDF 경로에 속하면 중단한다. 이전 preview만 사용하고 추출은 새로 요청하면 새 원문 폴더를 만든다.

폴더를 반환 직후 삭제하지 않는다. UI와 저장된 결과가 계속 이미지/원문을 참조하기 때문이다. 이번 변경으로 과거 폴더를 삭제하지 않았으며, 디스크 공간 회수는 저장 결과의 참조와 보존기간을 확인하는 별도 정책이 필요하다.

## 재현

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_pipeline_workspace.py -q
```

9개 시험에는 동시 요청의 근거 분리, 후속 실행·실패 실행의 기존 근거 보존, 추출 재사용, 다른 PDF 오연결 차단, 긴 파일명, 제공 D02의 실제 두 프로세스 동시 추출이 포함된다. 실제 두 프로세스의 추출 JSON SHA256/집계는 같고 경로는 다르며, UI raw JSON 로더의 연결도 확인한다. CLOVA 호출은 하지 않는다. D02가 없는 환경에서는 해당 실제 통합시험을 skip하므로 실행 여부를 함께 확인한다.

이 변경은 **추출 작업파일 격리**다. 동일한 pipeline 객체를 여러 스레드에서 재사용하는 API, PyMuPDF의 스레드 안전성, 최종 UI CSV/피클 캐시의 프로세스 간 동시 쓰기 잠금, 실행 중 원본 파일을 제자리에서 교체하는 상황까지 해결한 것은 아니다. 현재 UI는 요청별 pipeline 객체를 만들며 실제 병렬 통합시험도 별도 프로세스로 수행한다.
